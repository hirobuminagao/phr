## 結論

付属2の322 namecodeは、`exam_item_master`に全件存在する。DB欠落は0件。

現在DBで保持している以下の項目は、XML用単位の15件を除き、公式値と一致または表記正規化後に一致した。

- 項目名
- XMLデータ型
- 項目コードOID
- 結果コードOID
- 表示用単位
- XML用単位
- 検査方法
- 区分番号・区分名称・順番号
- データタイプ
- XML検査方法コード
- 同一性項目コード・名称
- 一連検査グループ識別・関係コード

ただし、XML構造を正しく往復させる観点では未対応がある。このため「付属2を完全に表現できている」とは判定できない。

## 重要な不一致

### 1. author要素を表現できない

付属2で`author要素`が指定される診断・意見行は18行、参照される医師・歯科医師名namecodeは12種類ある。

現スキーマには「どの診断項目のauthorとして医師名を格納するか」を保持する列がない。特に以下4項目は、独立したobservationを読むXPathとして登録されている。

- `9N516000000000049` 健康診断を実施した医師の氏名
- `9N526000000000049` 意見を述べた医師の氏名
- `9N536000000000049` 健康診断を実施した歯科医師の氏名
- `9N546000000000049` 意見を述べた歯科医師の氏名

付属2上は独立observationではなく、対応する診断・意見observationの`author`として表現する。現在のマスタ定義のままではimportで見落とし、exportで独立observationにする可能性がある。

### 2. XPath/value_methodが未設定

- `xpath_template`未設定: 196 / 322行
- 型から期待される`value_method`未設定または相違: author対象を除き184行

現行XML importerはマスタXPathを使わず再帰的にobservationを読むため、直ちに全項目が取込不能という意味ではない。ただし、`exam_item_master`単独を正として汎用抽出・検証することはできない。

### 3. 付属2の検証制約を保持できない

現スキーマに列がなく、次の情報を行単位で保持できない。

- 最大バイト長: 322行すべてに指定
- 数値形式: 245行に指定
- XML化にあたっての備考: 68行に指定
- author対応: 18行に指定

最大バイト長と数値形式がないため、付属2準拠の入力時検証をマスタだけから生成できない。

### 4. XML用単位の相違

15行に相違がある。うち7行は公式が空欄なのにDBが`1`、残りは公式表記とDBのUCUM正規化表記が異なる。

- `9N091000000000001`: `{times}` / DB `1`
- `9N121000000000001`: ``{h`b}/min`` / DB `1/min`
- `8A065000002391901`: `ml/min/1.73m2` / DB `mL/min/{1.73_m2}`
- `3A016000002327102`: 空欄 / DB `1`
- `1A030000000190301`: 空欄 / DB `1`
- `1A030000000199901`: 空欄 / DB `1`
- `3A015000000106128`, `3A015000000199928`: `mg/g*CR` / DB `mg/g{creat}`
- `3A015000000406126`, `3A015000000499926`: `mg/day` / DB `mg/d`
- `2A010000001930101`: `/mm3` / DB `1/mm3`
- `9E160162100000001`, `9E160162500000001`, `9E160162200000001`, `9E160162600000001`: 空欄 / DB `1`

DB側の方が一般的なUCUM表記に近いものもあるが、厚労省XMLへ出力する値として公式文字列を要求するなら差異になる。内部正規化単位と出力単位を分離するのが安全。

### 5. 備考が未反映

公式`備考`がある180行で、DB `notes`が空または不一致。XML値そのものには直結しないが、条件・運用上の注意をマスタから確認できない。

## 一連検査

付属2で一連検査グループ指定がある53行は、DBのグループ識別と関係コードが全件一致した。心電図、胸部X線、眼底等の`COMP`/`RSON`関係はマスタ上は表現できている。

## DBにだけ存在する項目

DBには付属2 Ver.4にない拡張項目が50行ある。独自追加または別マスタ由来の項目として区別されており、付属2の欠落ではない。行別CSVには公式322行だけを記録し、50 namecodeは監査生成時のJSON集計で確認した。

## 推奨する修正順

1. `author`親子関係を保持する列を追加し、import/exportを同じ定義で処理する。
2. 最大バイト長・数値形式・XML備考をマスタに追加する。
3. 15件のXML出力単位について、公式出力値と内部正規化値を分離する。
4. 未設定XPathを埋めるか、XPathを正としない設計なら列と利用箇所を整理する。
5. 公式備考を同期する。

## author対応の実装

この監査後、`annex2_author_item_code`を追加するmigration・seedと、XML import/exportのauthor対応を実装した。

- import: 親observationの`author/assignedAuthor/assignedPerson/name`を対応する医師名namecodeの値として取り込む。
- import互換: 従来の独立observation形式で医師名が存在する場合も読み込み、同じ値を重複生成しない。
- export: 医師名namecodeを独立observationとして出さず、対応する親observationのauthorとして出力する。
- seed: 付属2 Ver.4のauthor指定18行を全件登録する。
- XMLのauthorから生成した値は`exam_item_values.normalize_reason = XML_AUTHOR_ELEMENT`として記録する。
- 個人case一覧・詳細では、採用値にこの記録があるcaseを「author補完済み」と表示する。
- XML sourceにauthor対象の親項目があり、対応する医師名項目が存在しないcaseは「author未取得候補」と表示・絞り込みできる。元XMLにauthor自体がない場合も含むため、取込漏れの断定ではなく再取込・原本確認の対象とする。
- 既存caseを「author補完済み」にするには、XML再取込後にcase採用値を再作成する必要がある。
