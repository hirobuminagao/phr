

# Identity Canonicalization Specification (v1.0.2)

## Overview

This specification defines the canonicalization and identity matching policy for PHR v1.0.2.

It operationalizes ADR-0012: *Identity Canonicalization and Join Hash Policy (v1.0.2)*.

The goal is to ensure consistent identity matching across the following tables:

- `dev_phr.subscribers`
- `work_other.hia_dashboard_status`
- `work_other.hia_person_years`

These tables originate from different pipelines:

- HUB subscriber CSV
- HIA dashboard CSV
- HIA export XML

Because these sources normalize identity data differently, a unified canonicalization layer is required.

---

# 1. Core Principle: raw / match / hash

All identity fields follow a **three-layer structure**.

## 1.1 raw

The original value must always be preserved.

Examples:

- XML original values
- CSV original values
- dashboard exported values

These are kept for:

- traceability
- debugging
- audit
- recomputation

Raw values must never be destroyed or overwritten.

---

## 1.2 match

`match` values are canonicalized values used for **identity comparison**.

These values are generated by applying normalization rules.

Typical transformations:

- Unicode normalization (NFKC)
- trimming
- whitespace removal
- kana normalization
- kanji normalization via dictionary

Match values are used for:

- person matching
- deduplication
- cross-system joins

---

## 1.3 hash

When all required identity inputs are available, a hash column is generated.

Purpose:

- faster joins
- simplified SQL
- stable identity reference

The hash **does not replace raw or match values**.

---

# 2. Canonical Identity Input

The canonical identity input used across the system is:

```
person_id_custom
+ name_kana_full_match
+ gender_code
```

`person_id_custom` itself is derived from:

- insurer_number
- insurance_symbol
- insurance_number
- birthdate

This means the full identity key logically represents:

```
insurer_number
insurance_symbol
insurance_number
birthdate
name_kana_match
gender_code
```

---

# 3. Hash Identity Key

A join optimization key will be generated from:

```
person_id_custom | name_kana_full_match | gender_code
```

Hash algorithm:

```
SHA-256
```

Example canonical string:

```
01234567-00123-987654|ナガオヒロフミ|1
```

Result:

```
identity_hash
```

This hash enables extremely efficient joins across large tables.

---

# 4. Kanji Normalization

Kanji names require additional normalization because multiple Unicode forms exist.

Normalization steps:

1. Unicode NFKC normalization
2. trim
3. whitespace removal
4. apply kanji normalization dictionary

Example conversions:

| Original | Canonical |
|--------|--------|
| 羽 | 羽 |
| 神 | 神 |
| 塚 | 塚 |
| 礼 | 礼 |
| 猪 | 猪 |
| 﨑 | 崎 |
| 瀨 | 瀬 |
| 髙 | 高 |

These mappings are stored in a database dictionary table.

---

# 5. Kana Normalization

Kana normalization must ensure stable matching.

Rules include:

- convert half-width kana → full-width
- convert hiragana → katakana
- normalize small kana

Example:

```
ャ → ヤ
ュ → ユ
ョ → ヨ
ッ → ツ
```

Whitespace must be removed.

---

# 6. Normalization Dictionary

Kanji normalization will be implemented via a dictionary table in `dev_phr`.

Example table:

```
identity_kanji_normalization
```

Structure example:

| original_char | normalized_char |
|---------------|----------------|
| 羽 | 羽 |
| 神 | 神 |
| 塚 | 塚 |
| 礼 | 礼 |

The system may apply this mapping iteratively per character.

# 7. Target Tables

The following tables will adopt the canonicalization policy.

## subscribers

Location:

```
dev_phr.subscribers
```

Columns to standardize:

- `name_kana_full_match`
- `name_full_match`
- `identity_hash`

---

## dashboard

Location:

```
work_other.hia_dashboard_status
```

Changes:

- add `name_kana_full_match`
- add `identity_hash`

---

## person_years

Location:

```
work_other.hia_person_years
```

Changes:

- improve `name_kana_norm`
- add `identity_hash`

---

# 8. Backfill Strategy

Existing data must be recalculated.

Backfill scripts will:

1. recompute match columns
2. apply kanji dictionary
3. regenerate identity_hash

This ensures legacy rows follow the same identity model.

---

# 9. Future Extensions

Possible future improvements include:

- multi-character normalization (渡邉 → 渡辺)
- advanced regex normalization
- UI-safe font normalization

These are outside the v1.0.2 scope.

---

# Summary

Identity handling in PHR follows three rules:

```
1. Never discard raw values
2. Always generate match values
3. Generate hash when inputs exist
```

This architecture ensures:

- traceability
- consistent identity resolution
- scalable joins

It becomes the foundation for identity matching across all PHR subsystems.
