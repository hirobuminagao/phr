

# v1.1.0 identity layer commonization

## 1. Purpose

本specは、v1.1.0 における identity 系処理の共通レイヤー化方針を定義する。

対象は、人物識別に関わる `raw / match / hash` の扱い、`person_id_custom` 生成に必要な canonicalization、既存データへの backfill 手順、および各パイプラインへの適用方針である。

本specは ADR-0016 を受けた実装仕様であり、freeze 中に確定した v1.0.3 の挙動を土台として、責務分離と横展開可能な構造を定めることを目的とする。

---

## 2. Scope

本specの対象は以下とする。

- `medi_xml_ledger` の identity 系列
- `subscribers` の identity 系列
- `staging_subscribers_hub` の identity 系列
- HIA import / HIA dashboard import における人物識別処理
- `custom_id_gen` の前段で必要な canonicalization
- `identity_hash` の材料生成処理
- 上記に対する backfill スクリプト

本specの対象外は以下とする。

- XML/CDA 出力仕様そのもの
- 業務判定ロジック
- 付属2や section code などの制度仕様整理
- DB 全面再設計

---

## 3. Design Principles

### 3.1 基本原則

identity 系処理は、必ず以下の三段構えで考える。

- `raw`
  - 入力元から受領した元値
  - 原則として意味変換しない
  - 追跡・監査・再判定の基準とする
- `match`
  - 比較・照合・JOIN・検索用の正規化値
  - 項目ごとにルール固定
- `hash`
  - 規定の canonical 値を材料にしたハッシュ値
  - 必須材料不足時は未生成を許容する

### 3.2 固定ルール

今後の identity 系正規化は、以下のルールを固定とする。

- 元の値は省かない
- `raw` は保持する
- 照合用として `match` を作る
- hash 材料が揃う場合は `hash` を作る
- `match` 系の英数字は半角とする
- `match` 系で数字列は先頭0を削除する
- 値の正規化は「全てが数字なら半角」「一文字でも数字以外が入るなら全部全角（厚生労働省フォーマット）」を原則とする

### 3.3 責務分離

以下は用途が異なるため、同じ処理として雑にまとめない。

- 受領値の保持
- 照合用正規化
- `person_id_custom` 用 canonicalization
- `identity_hash` 用 canonicalization
- DB更新・backfill

## 4. Target Columns / Data Units

identity 系で最低限扱うデータ単位は以下とする。

- 保険者番号
- 記号
- 番号
- 生年月日
- 氏名カナ
- 性別コード

必要に応じて、以下も周辺 identity 情報として扱う。

- 氏名漢字
- 枝番
- 受診日
- 医療機関コード
- ZIP / XML ファイル名

ただし、`person_id_custom` や `identity_hash` の材料に使う項目は、用途ごとに別途明示する。

## 5. Layer Structure

### 5.1 レイヤー全体像

v1.1.0 では、identity 共通レイヤーを少なくとも次の単位で分割する。

1. 文字基礎正規化層
2. 項目別 match 正規化層
3. canonical 値生成層
4. ID / hash 生成層
5. DB反映 / backfill 層

### 5.2 文字基礎正規化層

責務:
- NFKC 相当の文字整形
- 前後空白除去
- 半角/全角空白の吸収
- 区切り記号・ハイフン類・長音類の統一的除去または置換
- 比較前の基礎整形

この層では、まだ項目意味に踏み込まない。

### 5.3 項目別 match 正規化層

責務:
- 保険者番号の match 生成
- 記号の match 生成
- 番号の match 生成
- 生年月日の match 生成
- 氏名カナの match 生成

この層では、項目ごとの個別ルールを持つ。

### 5.4 canonical 値生成層

責務:
- `person_id_custom` 生成用 canonical 値を返す
- `identity_hash` 生成用 canonical 値を返す
- match 値があっても、hash 材料として不足なら不足を明示する

この層では「照合に使える値」と「ID/hash材料として使う値」を分ける。

### 5.5 ID / hash 生成層

責務:
- `person_id_custom` の生成
- `identity_hash` の生成
- 生成可否の判定
- 材料欠損時のスキップ制御

### 5.6 DB反映 / backfill 層

責務:
- 対象レコードの抽出
- `raw` / `match` / `person_id_custom` / `identity_hash` の更新
- 件数集計
- 差分確認
- dry-run / 本更新の切り替え

## 6. Match Normalization Rules

### 6.1 保険者番号

方針:
- 基礎正規化後、数字のみを対象とする
- 全て数字なら半角化する
- 先頭0を削除する
- 空文字化した場合は `None` 相当で扱う

### 6.2 記号

方針:
- 基礎正規化後、区切り文字・空白・ハイフン類・長音類を除去する
- 数字だけなら半角化し、先頭0を削除する
- 数字以外を含む場合は全体を全角へ寄せる
- 比較用として揺れを吸収する

備考:
- HIA export ZIP v1 で確定した `insurance_symbol_match` 正規化手順をデフォルトとする

### 6.3 番号

方針:
- 基礎正規化後、数字のみを対象とする
- 半角化する
- 先頭0を削除する
- 空文字化した場合は未設定扱いとする

### 6.4 生年月日

方針:
- 入力形式の揺れを吸収する
- canonical な日付表現へ変換する
- `match` 用と ID/hash 用で必要な表現差がある場合は用途別関数で分ける

例:
- `YYYY-MM-DD` 系
- `YYYYMMDD` 系

### 6.5 氏名カナ

方針:
- 全角カタカナへ寄せる
- 半角カナを吸収する
- ひらがなをカタカナへ寄せる
- 半角/全角空白を除去する
- 中黒を除去する
- ダッシュ/長音符揺れは別途ルールを定めて吸収する

## 7. Canonicalization for person_id_custom / identity_hash

### 7.1 基本方針

`match` 値と `person_id_custom` / `identity_hash` 用 canonical 値は、似ていても同一視しない。

理由:
- `match` は比較用途
- `person_id_custom` は固定手順のID生成用途
- `identity_hash` は hash 材料用途

### 7.2 person_id_custom 用 canonical 値

デフォルトの入力順は以下とする。

1. `birthdate`
2. `insurance_number`
3. `insurer_number`
4. `insurance_symbol`

方針:
- 各項目は ID 生成用の前処理を通す
- 実効桁判定は、先頭ゼロ正規化後の値で行う
- `custom_id_gen` の固定ルールをそのまま利用する
- 材料欠損時は未生成を許容する

### 7.3 identity_hash 用 canonical 値

方針:
- hash 用に必要な項目セットを明示する
- 項目順・結合方法・欠損時の扱いを固定する
- `match` 値の流用で足りない場合は専用 canonical 値を作る

### 7.4 canonicalization 結果の扱い

各生成関数は、少なくとも次を返せる構造が望ましい。

- 正規化後値
- 未生成理由または不足項目
- 生成可否フラグ

## 8. Backfill Policy

### 8.1 実行順序

backfill は、原則として以下の順で実行する。

1. `raw` の存在確認
2. `match` の生成・更新
3. `person_id_custom` の生成・更新
4. `identity_hash` の生成・更新
5. 件数確認・監査ログ確認

### 8.2 更新原則

- 元値が無いものを推測で補わない
- 既存値がある場合でも、ルール変更対象なら再計算対象にできるようにする
- dry-run を基本装備とする
- 差分件数を出す
- 更新前後のサンプル確認ができるようにする

### 8.3 テーブル単位の実施

backfill は、原則としてテーブル単位で分ける。

例:
- `medi_xml_ledger` 用 backfill
- `subscribers` 用 backfill
- HIA dashboard import 用 backfill

### 8.4 監査観点

最低限、以下を確認対象とする。

- 対象件数
- 更新件数
- 未生成件数
- 未生成理由の内訳
- 主要キーごとの差分例

---

## 9. Expected Module Responsibilities

実装時は、少なくとも次の責務単位でライブラリ化することを想定する。

- `base_normalizer`
- `match_normalizer`
- `canonical_builder`
- `person_id_service`
- `identity_hash_service`
- `backfill_runner`

実ファイル名や配置は実装時に確定するが、責務の混在は避ける。

---

## 10. Application Order

v1.1.0 では、以下の順で適用する想定とする。

1. spec 固定
2. 共通関数の配置先確定
3. `medi` 系への先行適用
4. `subscriber` 系への適用
5. HIA import / dashboard 系への適用
6. backfill 実施
7. 検証結果を spec / ADR に反映

---

## 11. Non-goals

v1.1.0 では、以下は目的としない。

- 全パイプラインの一括全面書き換え
- freeze 中ロジックの業務仕様変更
- DB設計の大規模変更
- XML出力仕様の変更

---

## 12. Notes

- 本specは、まず責務境界を固定するための親specである
- 詳細な I/O 仕様、関数シグネチャ、テーブル別 backfill 手順は必要に応じて子specへ分離する
- 実装途中で差異が出た場合は、ADR → spec → 実装の順で整合を取る
