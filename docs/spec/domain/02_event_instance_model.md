# Event Instance Model

# version: draft
# owner: hiro
# updated: 2026-04-01

---

## 1. 目的

本ドキュメントは、event（イベント枠）に属して発生する event_instance（イベントインスタンス）として何が存在するかを定義することを目的とする。

本ドキュメントでは、イベントの識別子（event_id）やテーブル設計には踏み込まず、
イベントの構成要素と粒度の整理に留める。

本ドキュメントは 01_event_model_overview.md に定義された event（イベント枠）を前提とする。

---

## 2. イベントインスタンスの定義

イベントインスタンスとは、

**人に対して実際に発生した業務上の出来事**

を指す。

本ドキュメントにおいて、event は制度・年度・種別などにより定義される「イベント枠」を指す。
event は人に直接紐づくものではなく、実際の出来事は event_instance（イベントインスタンス）として発生する。

健診および特定保健指導において、event_instance は以下の3種類に分類される：
- 実施 event_instance
- 結果 event_instance
- 請求 event_instance（健診のみ）

---

## 3. 実施 event_instance

### 3.1 定義

対象者に対して実際に行われた行為。

### 3.2 種類

#### 健診
- 予約
- 受診（実施）

#### 特定保健指導
- 予約
- 初回面接
- 継続支援
- 最終評価

### 3.3 粒度

- 「1回の実施」を1イベントとする
- 同一年度内でも複数回発生しうる（例：継続支援）

---

## 4. 結果 event_instance

### 4.1 定義

実施イベントの結果として生成されるデータ。

### 4.2 種類

#### 健診結果
- 数値データ（検査値）
- 判定結果
- XML形式データ

- HIAダッシュボード状態（未予約 / 予約済み / 受診済み / 結果登録済み）

#### 特定保健指導結果
- 支援記録
- アウトカム
- 評価結果

### 4.3 特徴

- 実施イベントと1対1とは限らない
- 複数経路から生成・登録される

- HIAダッシュボード由来の状態は、最新参照ではなく観測時点の値として扱う
- HIAダッシュボードは run ごとに上書きされ、年度切替時に状態が初期化されうる
- そのため、イベント判定に必要な値は event_instance 側へ記帳して保持する

---

## 5. 請求 event_instance

### 5.1 定義

健診実施に対して発生する費用情報。

### 5.2 構成要素

- 総額（医療機関請求額）
- 健保負担
- 事業所負担
- 自己負担

### 5.3 特徴

- 健診にのみ存在する
- 結果とは別タイミングで確定する場合がある

---

## 6. 人との関係

event は人に直接紐づくものではなく、event_instance を通じて人と関係する。

ただし現行システムでは：

- 実施は人に紐づいている
- 結果はファイル単位で管理されている
- 請求は人単位で統合されていない

そのため、人を中心とした一貫した管理ができていない。

また、人の同一性は `person_id_custom` および `identity_hash` により横断的に担保する。
これにより、複数システム間で分断されている実施・結果・請求データを人単位で統合可能とする。

なお、HIA状態や納品状態のような「人の現在状態・観測状態」は人履歴側で保持し、
受診・支援などの実施はイベント側で管理する。

具体的には、受診・面談・支援・結果・請求といった実際の出来事は event_instance として人に紐づく。

実施・結果・請求は person と event に紐づく event_instance として結合される。

---

## 7. 同一イベント束の考え方

以下の event_instance は別々に存在してよい：
- 実施
- 結果
- 請求

ただし、

**同一の健診または指導に属するものは、1つの event（イベント枠）に属する event_instance 群として束ねて扱う必要がある**

event_id は event（イベント枠）を識別する内部識別子である。

本モデルでは、この「イベント束」は event_id により識別される event（イベント枠）に属するものとして扱う。
一方で、実際の実施（受診・面談・継続支援など）は event_instance として別に発生する。
結果および請求は、同一 event_id に属する event_instance に関連づくデータとして扱う。

---


## 8. 現状課題

- 結果が人・実施と結びついていない
- 請求がイベント単位で管理されていない
- 同一 event に属する event_instance 群としての概念が存在しない
- 複数経路のデータが統合されていない


### 8.1 健診における具体的問題

現行の健診運用において、以下の問題が発生している：

- 結果アップロード時に、照合成功/失敗およびエラー内容が確認できない
- 納品用結果ダウンロードにおいて、出力されない対象者が存在する（条件不明）
- 人の履歴管理がないため、同一人物が複数月に重複して出力される

これにより、データの完全性および再現性が担保されていない。

その結果として、以下の運用対応が発生している：

- 2025年度は医療機関による直接アップロードを行わず、弊社が代理アップロードを実施
- 健保への納品はHIAからダウンロード後、重複を除外して再加工している

また、現行システムでは上記課題に対応できないため、ローカル環境でイベント管理の仕組みを別途構築している。

### 8.2 根本原因

上記の問題は、イベント単位での識別および人単位での履歴管理が存在しないことに起因する。

- 実施・結果・請求が同一単位で管理されていない
- システム間で人およびイベントの一貫した識別子が存在しない
- 時系列としての状態遷移が保持されていない

さらに、人の履歴（加入者情報の変遷、状態遷移、結果受領状況）が保持されていないため、
ある時点における「正しい状態」を再現することができない。

### 8.3 v1.1.0 における現在対応

上記課題への対応の一環として、v1.1.0 ではローカル側に以下の補助基盤を構築している。

- 医療機関から受領した健診データの格納
- 加入者情報の最新版および履歴の保持
- HIAダッシュボード状態の保持
- HIAから取得した納品用XMLの格納

これらのデータには `person_id_custom` および `identity_hash` を付与し、人単位で横断的に追跡・照合できるようにしている。

さらに、v1.1.0 ではイベントテーブルを導入し、実施・結果・請求をイベント単位で記帳できる構造へ移行することを目的としている。

これにより、加入者リストを基準として年度単位で以下を確認できる状態を目指している。

- 健診結果を受領しているか
- HIAダッシュボード上でどの状態にあるか
- 健保への納品対象として出力・納品されているか

その結果、対象者ごとに「どの段階で何が欠けているか」「どこでズレが発生しているか」を明確にできる。

なお、v1.1.0 ではイベント統合に先立ち、人履歴の補完基盤としての役割を持つ。
イベントテーブルはこの人履歴を基準として記帳され、将来的なイベント統合の土台となる。

## 8.4 v1.1.0 のスコープ

v1.1.0 では、まず健診（定期健診）を対象とし、以下の可視化を実現することを目的とする。

- 加入者単位での健診結果受領有無
- HIAダッシュボード上の状態
- 健保への納品対象および納品状態

これにより、対象者ごとにどの段階でデータが欠落または不整合となっているかを特定可能とする。

## 9. 次段で定義するもの

本ドキュメントでは扱わないが、次の設計で定義する：

- event_id の詳細設計（識別子生成および属性管理）
- event テーブル構造
- event_instance の管理構造
- データ統合ロジック（実施・結果・請求の紐付け）

---

## 10. システム構造

本ドメインは主に以下のシステムで構成される。

- 健診予約システム（予約・受診ステータス・結果アップロード）
- HIA（加入者管理・状態管理・データ登録/ダウンロード）
- 特定保健指導システム（予約・実施・報告作成）

これらは相互に連携するが、同一の識別子や状態管理を共有していない。

---

## 11. データの本体

健診結果および特定保健指導データの本体は、S3に保存されたXMLである。

- CSVで受領したデータも最終的にはXMLに変換される
- DBは参照・補助用途であり、完全な再現はXMLを参照する必要がある

---

## 12. 予約システムの特性

- 仮予約〜受診完了まで同一IDで状態遷移する
- 状態は可変であり、キャンセル・変更が可能
- 仮予約は外部連携対象外（現時点）

---

## 13. HIAの特性

HIAは人単位で状態を管理する。

ステータス：
- 未予約
- 予約済み
- 受診済み
- 結果登録済み

特性：
- 予約済みまでは可逆（変更・キャンセル可能）
- 受診済み以降は不可逆（通常操作で戻せない）

### 13.1 HIAダッシュボード由来データの扱い

HIAダッシュボードは「現在状態」を表すスナップショットであり、同一人物の状態は run ごとに上書きされる。

そのため、イベント（event）に対する状態判定を hia_dashboard_status の最新値参照で行ってはならない。

イベントに必要な情報は、観測時点の事実として event_instance に記帳する。

記帳時には、少なくとも以下を保持する。
- event_id
- subscriber_id
- run_id
- instance_type = HIA_STATUS_OBSERVED
- instance_status = ダッシュボード状態
- payload_json = 観測時点のダッシュボード値

これにより、次年度 run により HIA状態が未予約へ初期化された場合でも、前年度 event に属する状態を event_instance 側で保持できる。

run_id は、どのスナップショット時点の状態かを示す証跡として扱う。必要時のみ、run_id を起点に差分履歴から再現可能とする。

---

## 14. 加入者照合の実態

- 照合はrawデータで行われる
- 照合専用カラムは存在しない
- 各処理・画面ごとにロジックが分散している

そのため、照合結果の一貫性は保証されない。

---

## 15. 結果データの扱い

- 結果データは欠損の有無に関わらず格納される
- 加入者照合に成功した場合のみ人に紐づく
- 「結果登録済み」は照合完了状態を指す

---

## 16. 健診の構造

健診は単発の event_instance を中心とする。

- 予約
- 実施
- 結果
- 請求

これらは同一の event_id に属する構成要素であり、個々の受診や結果受領は event_instance 側で発生する。

なお、「予約」は事前状態を表すものであり、実施・結果・請求とは性質が異なる。
実施以降のデータは実際に発生した事実として扱い、イベントの確定情報として扱う。

---

## 17. 特定保健指導の構造

特定保健指導は、1つの event に属する複数の event_instance が連続するプロセス型である。

- 年度につき1回実施
- 初回面談〜最終評価まで連続して進行

特定保健指導全体は1つの event_id に属するが、初回面談や継続支援の各実施は event_instance 側で発生する。

### 継続支援

継続支援は単一イベントではなくプロセスである。

- 定期的な入力依頼
- 対象者入力（体重・腹囲・コメント等）
- 指導者確認
- 指導者アドバイス

これを複数回（4期では6回）繰り返す。

---

## 18. 年度の非一致

特定保健指導は、過去年度の健診結果を基に実施される場合がある。

そのため、イベント年度と参照する健診結果の年度は一致しない。
