# 申し送り・注意事項・改修要望機能案

## 1. 位置づけ

本書は将来実装候補の整理であり、現時点の確定仕様ではない。

運用中に発生する次の情報を、個人メモや口頭連絡だけに残さず、対象データと関係者へ結び付けて追跡できるようにする。

- 健診機関への確認依頼。
- 担当者間の申し送り。
- 健診機関または受領フォルダaliasに固有の恒久的な注意事項。
- システムの改修要望。

申し送りと改修要望を同じ機能・テーブルにするかは未決定とする。画面導線、関係者、コメント、関連リンク、既読管理などの共通化候補はあるが、業務対応と開発管理では状態遷移や権限が異なる可能性がある。

## 2. 想定例

```text
件名: CSV、XMLに医師名なし
種別: 健診機関確認
対象: 健診機関、受領フォルダalias、イベント
項目: 9N516000000000049 医師名
対応方針: 健診機関へ確認
起票者: 問題を発見した担当者
担当者: 確認と回答反映を行う担当者
確認先: 健診機関
状態: 回答待ち
```

## 3. 情報の種類

### 3.1 申し送り・確認依頼

- 一時的な作業や確認を追跡する。
- 状態、担当者、期限、回答、完了を持つ。
- 健診機関確認、社内確認、保険者確認などの確認先を区別する。

状態候補:

- `OPEN`: 未対応。
- `IN_PROGRESS`: 対応中。
- `WAITING_RESPONSE`: 回答待ち。
- `RESOLVED`: 対応済み。
- `CLOSED_NO_ACTION`: 対応不要・見送り。

### 3.2 健診機関・alias注意事項

- 次回以降も参照する恒久情報を扱う。
- 健診機関全体の注意事項と、特定aliasだけの注意事項を分ける。
- CSVの列構成、文字コード、紙補完が必要な項目、連絡時の注意などを想定する。
- 申し送りの回答を、恒久注意事項へ昇格できる導線を検討する。

### 3.3 改修要望

- 業務データの確認依頼とは別種別として扱う。
- 要望、背景、期待結果、影響画面、暫定回避策、優先度を記録する。
- 状態候補は `REQUESTED`、`UNDER_REVIEW`、`PLANNED`、`IMPLEMENTING`、`RELEASED`、`REJECTED` とする。
- GitHub issue等の外部開発管理へ移した場合も、そのリンクと移管状態を残せるようにする。

## 4. 関係者

最低限、次を区別する。

- 起票者: 最初に問題や要望を登録した人。
- 担当者: 次の対応を行う人。
- 確認先: 健診機関、保険者、社内担当など。
- 関係者: 更新通知を受け取るユーザー。

担当変更、状態変更、コメント追加、期限変更は履歴として残す。本文の上書きだけで過去判断を失わない構造とする。

## 5. 関連リンク

1件の申し送り・注意事項・改修要望に、複数の業務対象を関連付けられるようにする。

対象候補:

- event ID。
- case ID。
- ledger ID。
- 健診機関ID。
- 受領フォルダalias ID。
- 出力リストID。
- CSVマッピングテンプレートID。
- namecode・法定明細番号。
- 任意の管理画面または外部課題URL。

本文へURLを直接埋め込むだけではなく、`target_type + target_id`から表示名と画面URLを生成できる関連テーブルを検討する。リンク先の閲覧権限がないユーザーには、機微情報やリンクを表示しない。

case詳細、健診機関詳細、alias管理、CSVマッピング画面などから起票した場合は、その画面の対象IDを自動で関連先へ追加する。

## 6. 通知と既読

HOMEおよび共通ヘッダーにベルアイコンを置き、ユーザーごとの未読件数を表示する。

通知対象候補:

- 自分が担当者に設定された。
- 自分が起票した内容に回答・コメントが追加された。
- 状態や期限が変更された。
- 回答待ちまたは期限超過になった。
- 関係者またはメンション対象に設定された。

既読状態と業務状態は分離する。

- 既読・未読: 各ユーザーが通知を確認したか。
- OPEN・回答待ち・完了等: 業務としての対応状態。

ベル押下時は通知ドロワーを表示し、関連するcase、健診機関、alias、マッピング等へ直接移動できるようにする。「すべて既読」と「申し送り一覧を開く」も設ける。

## 7. 画面候補

- HOME・共通ヘッダー: ベル、未読件数、通知ドロワー。
- 申し送り一覧: 担当、起票、確認先、状態、期限、対象で絞り込み。
- 申し送り詳細: 本文、関係者、関連リンク、コメント、変更履歴。
- 健診機関詳細: 施設全体の注意事項と未完了申し送り。
- alias詳細: alias固有の注意事項と未完了申し送り。
- 改修要望一覧・詳細: 業務申し送りと別種別・別表示を基本候補とする。

## 8. 実装前に決めること

- 申し送りと改修要望を同一テーブルにするか、共通基盤だけ共有して分けるか。
- 健診機関・alias注意事項を同じテーブルの種別で持つか、恒久メモとして分離するか。
- 通知対象の自動決定、メンション、メール等の外部通知範囲。
- 完了後の編集可否、再オープン、削除ではなく無効化する方針。
- 個人caseを関連付けた際の権限・マスク表示・監査ログ。
- 改修要望とGitHub issue等との連携方針。

## 9. 初期実装候補

1. 健診機関・alias・caseへの申し送り起票。
2. 起票者、担当者、確認先、状態、期限、本文の保持。
3. 複数関連リンクとコメント・変更履歴。
4. 担当・起票・状態別の一覧。
5. HOMEのベル、未読件数、通知ドロワー。
6. 健診機関・aliasの恒久注意事項。
7. 改修要望種別または専用管理への拡張。
