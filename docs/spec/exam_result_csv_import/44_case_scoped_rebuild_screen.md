# 対象者別 case再実行画面

## 1. 目的

event全件のcase処理を回さず、運用担当者が加入者1人の状態を確認して必要な範囲だけ再実行する。

- 既存caseがある加入者は、そのcaseだけを更新する。
- caseがなくても利用可能なledgerがある加入者は、case作成から開始する。
- 実行前に対象case、構成元ledger、現在の状態を画面で確認できるようにする。

## 2. 実装場所

- URL: `/exam-case-rebuild`
- 画面: `apps/health_exam_admin/templates/exam_case_rebuild.html`
- 画面処理: `apps/health_exam_admin/main.py`
- CSS/操作: `apps/health_exam_admin/static/app.css`, `apps/health_exam_admin/static/app.js`
- case作成: `scripts/from_medical/03_01_build_exam_export_cases.py`

HOMEと健診結果処理実行画面から遷移できる。利用権限は健診結果処理実行と同じ判定を使う。

## 3. 検索仕様

最初にeventを選択する。検索結果は最大50人とし、条件未入力では候補を表示しない。

### 加入者条件

次の項目を1行に表示し、すべて部分一致で検索する。

- HIA加入者ID
- 記号
- 番号
- 生年月日
- 氏名かな

複数条件を入力した場合はANDで結合する。生年月日は文字列表現に対する部分一致のため、`2026-05` のような年月指定も可能である。

### 健診条件

次の項目を2行目に表示する。

- 健診機関
- 受診月

健診機関は既存の健診機関マスタ検索モーダルから1施設を選択し、内部の `exam_facility_id` を検索値として保持する。選択は解除できる。

受診月は `YYYY-MM` で指定する。候補月は、選択eventの `exam_export_cases.exam_date` と `exam_ledgers.exam_date` の和集合から新しい順に最大36か月表示する。

健診機関・受診月の対象加入者は次の両方から検索する。

1. `health_exam_result.exam_export_cases`
2. `health_exam_result.exam_ledgers`

ledgerは `subscriber_id` を優先し、手入力ではdraftの `subscriber_id`、必要時は `hia_subscriber_id` から加入者を解決する。これにより、case未作成でもledgerが存在する加入者を候補にできる。

加入者条件と健診条件を同時に指定した場合は、健診条件で得た加入者集合に加入者条件をANDで適用する。

## 4. 対象者選択後の表示

候補から加入者を1人選択すると、次を表示する。

- subscriber ID、社員番号、HIA加入者ID、生年月日
- event内の既存case
- case作成元にできるledger
- caseのsource件数、採用値件数、readiness/check状態
- ledgerの形式、受診日、健診機関、ファイル、check状態、紐づくcase

検索条件は候補選択後もURLへ引き継ぐ。

## 5. 再実行仕様

### 既存caseがある場合

同じ加入者に複数caseがある場合は、再実行するcaseをチェックボックスで選択する。選択できる処理範囲は次の3種類である。

| 画面上の選択 | 実行する処理 |
| --- | --- |
| case構成から | `03_01` → `03_02` → `03_04` |
| 採用値から | `03_02` → `03_04` |
| 最終チェックだけ | `03_04` |

各処理には選択した `--case-id` を渡す。選択加入者に属さないcase IDは受け付けない。

### caseがない場合

利用可能なledgerが1件以上あれば、`03_01` を `--subscriber-id` 指定で実行する。その後、作成されたcase IDだけに限定して `03_02` と `03_04` を実行する。

caseも利用可能なledgerもない場合は実行できない。

### 共通制御

- 同じeventで健診結果処理が実行中の場合は開始しない。
- 各stepでエラーが発生した場合は後続stepを実行しない。
- 実行結果はstepごとに画面へ表示する。
- この画面では `03_05` の出力リスト作成を自動実行しない。
- `03_02` は採用値とcheck状態を再構築するため、必ず `03_04` まで続ける。

## 6. 複数加入者処理

2026-08-31時点では、加入者候補の複数選択と一括再実行は実装しない。

加入者ごとに次の状態が混在し、単純な一括処理では実行内容が不明瞭になるためである。

- caseあり／なし
- ledgerあり／なし
- caseが1件／複数件
- case構成から／採用値から／最終チェックだけ
- 一部加入者だけ失敗した場合の継続・中断

一括処理を実装する場合は、実運用のパターンを収集した後、少なくとも次を要件として決定する。

- 同一健診機関・同一受診月など対象集合の固定方法
- case作成対象、更新対象、対象外の事前件数表示
- 加入者ごとの処理範囲
- 一部失敗時の継続方針
- 再実行結果と監査ログの単位
- 確認モーダルと誤操作防止

それまでは、加入者1人を選び状態を確認してから実行する運用を現在正とする。
