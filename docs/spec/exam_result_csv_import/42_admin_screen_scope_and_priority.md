# 健診管理画面スコープと優先度

## 目的

健診結果取込、加入者、予約、HIAアップロード、紙健診、マスタ管理を社内ローカル画面で扱うための画面候補を整理する。

本ドキュメントは、画面実装の優先順位と責務境界を決めるための棚卸しである。
既存スクリプトやDBをすぐに置き換えるものではなく、画面化する作業単位を明確にする。

## 現在方針

- 画面は `apps/health_exam_admin` のFastAPI管理画面へ寄せる。
- 業務データの正は既存DBと既存スクリプト群に置き、画面は人の確認、補正、実行指示、状態記帳の入口とする。
- ログイン、ユーザー管理、個人別作業権限ON/OFFは実装済み。
- 作業権限はロールではなく個人ごとに `表示` / `編集・実行` をON/OFFする。
- 2択のON/OFF UIは、チェックボックスではなく有効/無効スイッチ部品を標準とする。
- 2026-08-21時点で、FastAPI管理画面は「HOME」「アカウント管理」「権限設定」「セキュリティ」「監査ログ」「イベント設定」「受領ファイル一覧」「健診結果一覧（受領）」「個人case一覧」「個人case詳細」「出力リスト一覧/詳細」「健診機関サマリー」「健診機関受領フォルダ管理」「HIAアップロード作業」「外部指摘・エラー記帳の初期版」「対象者リスト作成ユーティリティ初期版」まで実装済み。
- 個人case詳細では、case単位の確認事項記帳、採用値確認、基本情報補正を扱う。基本情報補正は出力用の `exam_export_cases` 現在値へ即時反映し、補正理由と履歴は `exam_case_basic_info_corrections` / `exam_case_basic_info_correction_audit_logs` に残す。
- 画面実装済みでも、業務上の最終運用が固まっていない画面は、まず確認・編集・台帳化の入口として扱う。

### HIAから健保へのXML納品

- HIAアップロード後に、HIAから取得したXMLを健保へ納品する工程は、HIA後工程として扱う。
- 既存の「同一人物を複数回納品しない」スクリプトは、2025年度後半に作った古い出力を残し、新しい出力から重複者を取り除く用途が中心だった。
- 今回は、整理前にHIAへアップロード済みのXMLがあり、その後に修正済みの新しいXMLを納品したいケースがある。
- そのため、後続リファクタリングでは「古い納品済みを常に優先して新しい方を落とす」だけでなく、修正版を正として納品対象にできるモードを持つ。
- 納品重複除外は、単なるファイル名比較ではなく、event、HIA加入者IDまたはsubscriber、健診日、健診機関、出力run、修正版/正式版の区別を見て判断する。
- 画面化する場合は、HIAアップロード状態、HIAからの取得状態、健保納品状態を人単位で確認できる導線を `健保納品管理` に置く。

### 健保管理

健保管理は、単なるマスタではなく、event、加入者、HIA、出力、納品に関わる業務設定を含むため、マスタ管理とは別メニューにする。

| 設定 | 目的 | 備考 |
|---|---|---|
| 健保基本情報 | 保険者番号、健保名、表示名を管理する | 加入者・HIA・出力の起点 |
| event設定 | 年度、基準日、保険者番号、対象範囲を管理する | `event_id` と業務年度の対応 |
| HIA連携設定 | HIA加入者ID、ダッシュボードCSV、アップロード単位を管理する | HIA系画面と連携 |
| 加入者アップロード設定 | fund/HIA由来の加入者CSV取込条件を管理する | 年度更新で使用 |
| 報告区分/健診プログラム設定 | event内の自動判定や例外設定を管理する | 40歳基準日等を含む |
| 出力先/納品設定 | XML出力先、HIAアップロード、健保/事業所納品の設定 | 後続納品管理にも接続 |

### 健診機関管理

健診機関管理は、施設マスタだけでなく、受領フォルダ、CSV/XML/紙入力、マッピング、施設別確認事項を含むため、マスタ管理とは別メニューにする。

| 設定 | 目的 | 備考 |
|---|---|---|
| 健診機関基本情報 | 健診機関番号、表示名、連絡先を管理する | `exam_facilities` |
| 健診機関受領フォルダ | scan時の施設解決を管理する | 受領フォルダ名との紐付け。`event_id + src_folder_raw` が一意 |
| CSVフォーマット | 施設別CSVのヘッダー、文字コード、バージョンを管理する | header確認も含む |
| CSVマッピング | CSV項目から基本情報・検査値へのマッピングを管理する | 最重要の施設別設定 |
| 紙健診テンプレート | 紙入力の施設別入力項目を管理する | 紙健診入力画面と連携 |
| 施設別normalize/独自値 | 施設固有の表記や独自値の確認方針を管理する | 共通辞書へ昇格するかは別判断 |
| 健診機関確認事項 | 医療機関への問い合わせ、回答、対応状況を管理する | namecode誤用、独自コード等 |

#### 健診機関受領フォルダの受領設定

健診機関受領フォルダは、単なるフォルダ名の名寄せだけでなく、event内のその健診機関フォルダをどう受領・取込する想定かを管理する入口とする。

aliasに保持する運用設定:

- 想定受領モード: `UNKNOWN` / `XML_ONLY` / `CSV_ONLY` / `XML_CSV_MERGE` / `PAPER_ONLY` / `XML_PAPER_MERGE` / `CSV_PAPER_MERGE` / `XML_CSV_PAPER_MERGE`
- 使用するCSVテンプレート: `csv_format_versions.csv_format_version_id`

責務分離:

- `medical_folder_aliases`: event内の受領フォルダに対する運用設定。scan/import前に「このフォルダはXMLのみか、CSVのみか、紙のみか、複数sourceを結合するか」「どのCSVテンプレートを使うか」を人が確認・設定する。
- `file_receipts`: 実際に受領・検出したファイルの台帳。XML/CSVの実績、sha256、取込状態、format照合結果を保持する。
- `csv_format_versions`: CSVテンプレート本体。ヘッダー、文字コード、format version、mapping versionを保持する。

このため、受領モードとCSVテンプレート参照は `medical_folder_aliases` に直持ちする。
同じ健診機関でもeventやフォルダ運用が変わる可能性があるため、健診機関マスタ本体ではなく `event_id + src_folder_raw` で一意なalias側に置く。

受領モードは現時点では `expected_source_mode` の1カラムで管理する。
XML/CSV/紙の3種類で最大8パターンに収まるため、初期運用では別テーブルや複数booleanへ分解しない。
画面上は8パターンを直接選ばせず、一覧フィルタ・登録・編集ともに `XML` / `CSV` / `紙` の組み合わせボタンで操作する。
未選択を `UNKNOWN`、選択された組み合わせを `expected_source_mode` の保存値へ変換する。
将来、受領source種別がさらに増える、または同一aliasで月別・契約別に組み合わせが変わる場合は、履歴テーブルまたはsource種別別の子テーブルへ切り出す。

将来、同一event・同一alias内で月別に受領方式やテンプレートが頻繁に変わる場合は、`medical_folder_alias_receipt_settings` のような履歴テーブルへ切り出し、`valid_from` / `valid_to` を持たせる。
初期運用では設定粒度を増やしすぎないため、alias直持ちを正式方針とする。

## 権限と個人情報表示

- 管理者は全機能を利用できる。
- 管理カテゴリは `business_settings.view` / `business_settings.manage` で制御し、初期設定では編集者も表示・操作できる。
- システム管理カテゴリは `users.manage` で制御し、初期設定では管理者のみ操作できる。
- 通常作業はロールではなく個人ごとの作業ON/OFFで制御する。
- 作業ON/OFFは `表示` と `編集・実行` を分ける。
- HIAアップロード担当は、原則として個人情報詳細を見ずにZIP、健診機関、出力リスト、アップロード状態だけ扱える導線を目指す。
- 個人情報を含む画面は、画面単位ではなく操作単位で表示権限を分ける必要がある。

初期の個人作業権限:

| 作業 | 表示 | 編集・実行 |
|---|---|---|
| 出力リスト | 出力リスト一覧・対象概要の参照 | リスト作成、case追加/除外 |
| XML出力 | 確認出力結果の参照 | official XML/ZIP出力 |
| HIAアップロード | アップロード対象ZIP一覧の参照 | アップロード完了/エラー記帳 |

## 実装順メモ

1. 出力リスト画面を既存CLI/DBへ接続する。実装済みの初期版では、リスト作成、一覧、詳細確認まで対応済み。
2. 受領ファイル一覧、統合ledger一覧を画面から確認できるようにする。実装済み。
3. event設定を画面から管理できるようにする。実装済み。
4. 健診機関管理で `exam_facilities` と `medical_folder_aliases` を作成・更新できるようにする。実装済み。
5. 健診機関サマリーを追加し、受領ファイル数、source/caseチェックOK/NG率、加入者突合課題、normalizeエラー、NG項目topを見られるようにする。実装済み。
6. 健診機関サマリーから、該当健診機関で絞ったcase一覧、健診結果一覧（受領）、受領ファイル一覧へ遷移できるようにする。実装済み。
7. 個人case詳細でsource、採用値、check、case確認項目を見られるようにする。初期版は実装済み。
8. 個人case詳細から、case確認項目単位で確認待ち、理由ありOK、再提出待ち等を保存できるようにする。初期版は実装済み。理由ありOKは `exam_case_check_review_items` ごとに理由必須とし、保存後は「健診結果処理実行」の step5〜7 再実行を案内する。
9. 基本情報補正と加入者突合NG修正を追加する。基本情報補正は個人case詳細に初期実装済み。加入者突合NG修正は、`exam_ledgers` の現在突合値を確定し、必要に応じて `subscribers` 由来の氏名カナ、記号、番号、枝番、住所等を出力用基本情報へ適用する。`exam_ledger_subscriber_match_audit_logs` には変更履歴、加入者情報適用有無、適用項目を残す。健診機関確認事項、基本情報補正、加入者突合修正、理由ありOKなどを記帳・変更した後は、case側に反映するため「健診結果処理実行」の step5〜7 を再実行する案内を画面にも出す。

11. 外部指摘・エラー記帳の初期版を作成する。初期版は実装済み。ただし、後続では「指摘リスト作成→対象追加→case毎に記帳」へ再設計する。
12. 対象者リスト作成ユーティリティを設計・実装する。外部指摘、HIAアップロード済み記帳、健保/事業所納品済み記帳、健診機関確認対象作成の共通部品とする。初期版はDB保存なしで、貼り付け解析、identity生成、subscriber/case候補表示まで実装済み。
13. HIAダッシュボードCSVアップロードと加入者アップロードを画面化する。
14. 予約情報CSVアップロード、予約突合、未受領管理へ進む。
15. 健保管理で加入者アップロード、HIA連携、出力/納品設定を扱えるようにする。
16. 健診機関管理でCSVマッピング、紙テンプレート、確認事項を扱えるようにする。
17. 紙健診入力は、入力モックとテンプレート構造を整理してから実装する。

### 外部指摘リスト

外部指摘は、HIA、健保、事業所など外部から返ってきたエラーや指摘を、作業者が追跡・記帳するための機能である。

初期版では、外部指摘を直接登録し、reportとitemを確認する画面を作成した。
ただし業務上は、直接1件ずつ記帳するより、まず指摘のまとまりを作り、その中へ対象caseを追加して、caseごとに対応状態を記帳する流れの方が自然である。

後続の正式フロー:

1. 指摘リストを作成する。
2. 指摘リストへ対象を追加する。
3. 追加されたcase、個人XML、項目単位で指摘を記帳する。
4. 対応状態を更新する。
5. 必要に応じて再提出待ち、再提出済み、対応不要、解決済みに進める。

指摘リストの作成単位:

- HIAアップロードエラー単位。
- 健保からの返戻・指摘単位。
- 事業所からの差戻し単位。
- 健診機関確認依頼単位。
- 手動作業記録単位。

対象追加方法:

- 1 caseを個別追加する。
- ZIPを指定し、ZIP内の個人XML/caseをまとめて追加する。
- 出力リストを指定し、リスト内caseをまとめて追加する。
- case検索結果から複数追加する。
- Excelやテキスト貼り付けから対象者候補を作り、突合後に追加する。

記帳単位:

- リスト全体: 指摘元、受領日、全体メモ、状態。
- 対象case: その人に対する指摘、対応状態、対応メモ。
- 項目単位: namecode、業務チェックID、XMLエラー箇所など、項目に紐づく指摘。

初期DB:

- `ops_external_feedback_reports`: 指摘リスト/受領単位。
- `ops_external_feedback_items`: 指摘明細。case、member、ZIP、namecode、check itemへ紐づける。
- `ops_external_feedback_item_audit_logs`: 指摘明細の変更履歴。

後続の見直し方針:

- 画面名は「外部指摘・エラー記帳」から「外部指摘リスト」へ寄せる。
- reportは単なる受領情報ではなく、作業箱として扱う。
- itemは、リストに追加されたcaseごとの作業行を中心にする。
- 項目単位の細かい指摘は、itemの子要素に分けるか、item内の項目参照列で初期運用するかを実装前に再確認する。

|---|---|---|
| 一人ずつ追加 | 1人だけ確認して追加する | HIA加入者ID、subscriber_id、case_id、社員番号、氏名カナ、記号+番号 |
| 複数まとめて追加 | Excelやテキストから複数人を一括で追加する | タブ区切り、カンマ区切り、任意デリミタ、列割当 |
| ZIPから追加 | ZIP内の個人XMLをまとめて対象化する | `xml_export_zip_id` |
| 出力リストから追加 | 出力リスト内caseをまとめて対象化する | `xml_export_list_id` |
| case検索から追加 | 既存case一覧を条件検索して追加する | event、健診機関、受診月、状態 |

複数まとめて追加の個人特定キー:

- identity hash材料:
  - 保険者番号。
  - 記号。
  - 番号。
  - 氏名カナ。
  - 生年月日。
  - 性別。
- HIA加入者ID。
- subscriber_id。
- 社員番号。
- case_id。

保険者番号の扱い:

- 保険者番号は貼り付け列から取得できる。
- 貼り付けデータに保険者番号がない場合は、画面上部の固定値として入力できる。
- 固定値と貼り付け列の両方がある場合は、行側の値を優先するかエラーにするかを実装前に決める。初期案は「行側を優先し、固定値と違う場合は警告」とする。

列割当:

- Excel貼り付けを最優先し、既定デリミタはタブとする。
- 区切り文字は、タブ、カンマ、ハイフン、スペース、任意文字を選べるようにする。
- 列ごとに意味を割り当てる。
- 関係ない列を含んだまま貼れるよう、列割当に `未使用` を必ず用意する。
- 先頭行をヘッダーとして無視できる。

列割当候補:

- 未使用。
- 保険者番号。
- 記号。
- 番号。
- 枝番。
- 氏名カナ。
- 氏名。
- 生年月日。
- 性別。
- HIA加入者ID。
- subscriber_id。
- case_id。
- 健診実施日。
- 健診機関コード。
- 社員番号。

入力例:

```text
保険者番号  記号  番号  氏名カナ  生年月日  性別
06139463    100   12345 サンプル タロウ 19750724 男
```

任意デリミタ例:

```text
06139463-100-12345-サンプルタロウ-19750724-男
```

突合優先順位:

1. `case_id` があればcase直指定。
2. `subscriber_id` があればsubscriber直指定。
3. `HIA加入者ID` があればHIA IDで突合。
4. `社員番号` があればevent/保険者番号で絞って突合。
5. identity hash材料が揃えばidentity hashで突合。
6. 足りない場合は、氏名カナ、記号番号、生年月日などで候補検索する。
7. 候補が1件なら追加候補、複数なら候補複数、0件なら未突合とする。

突合結果ステータス:

| 状態 | 意味 |
|---|---|
| 追加OK | caseまたはsubscriberが一意に解決できた |
| 既に追加済み | 対象リストに同じcase/加入者が既に入っている |
| 候補複数 | 複数候補があり、人の選択が必要 |
| 未突合 | 加入者候補が見つからない |
| 入力不足 | 指定された突合方法に必要な項目が足りない |
| caseなし | subscriberは見つかったが、対象eventのcaseがない |
| 対象外候補 | 資格や状態により注意が必要。ただし自動除外しない |

UIフロー:

1. 追加モードを選択する。
2. 一人ずつ追加、または複数まとめて追加で入力する。
3. 複数まとめて追加の場合は、貼り付け、区切り文字、列割当、固定保険者番号を設定する。
4. プレビューで行ごとの解釈結果を表示する。
5. 突合を実行する。
6. 突合結果を `追加OK` / `既に追加済み` / `候補複数` / `未突合` / `入力不足` で表示する。
7. 追加対象にチェックを入れ、指摘リスト、納品記帳、アップロード記帳などの目的先へ追加する。

DB仮案:

初期実装では画面内一時処理でもよい。2026-08-20時点の初期版は、DBへ保存せずPOSTされた貼り付け内容をその場で解析し、DBはsubscriber/case候補の参照にのみ使う。
ただし、作業者が途中保存したい、突合不能行を後から再確認したい、同じ貼り付け結果を複数リストへ流用したい場合は、DBに一時バッチを持つ。

候補テーブル:

- `ops_person_selection_batches`
  - 貼り付け/検索/ZIP/出力リストから作った対象者候補の一時箱。
  - 作成者、作成日時、用途、固定保険者番号、デリミタ、列割当JSON、メモを持つ。
- `ops_person_selection_rows`
  - 貼り付け1行または候補1件。
  - raw行、列ごとの解釈値、突合結果、候補subscriber/case、エラー理由を持つ。

初期実装判断:

- 外部指摘リストへの接続を最初の利用先にする。
- DB一時テーブルを作るかは、画面モック後に決める。
- 実装を急ぐ場合は、POSTした貼り付け内容をその場で解析し、確認画面に表示して、選択行だけリストへ追加する。
- ただし監査ログには、どの入力から何件追加したかを残す。

共通lib利用:

- 氏名カナ正規化。
- 記号、番号、枝番正規化。
- 保険者番号正規化。
- 生年月日正規化。
- 性別正規化。
- identity hash作成。
- HIA加入者ID、subscriber_id、社員番号、case_idによる検索。

設計上の注意:

- 必要列だけ綺麗に抜いて貼る運用を前提にしない。
- 余計な列、未使用列、空列、ヘッダー行、列数不一致を許容し、人が確認できるようにする。
- 個人情報を含むため、貼り付け内容の保存有無、保存期間、監査ログの粒度を実装前に決める。
- 社員番号は単独では重複し得るため、event、保険者番号、所属健保などの文脈で絞って扱う。
- 対象者リスト作成ユーティリティは、外部指摘専用にしない。HIA、健保、事業所、健診機関確認など複数用途へ接続できるよう、入力解決と目的先追加を分離する。
