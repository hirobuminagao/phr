# 人×イベント 健診進捗照会 設計レビュー

## 結論

`person_event` を親、`person_event_status_items` を一覧用読み取りモデル、各業務テーブルを正本とする構成は、既存方針と整合する。1枚の巨大な横断SQLまたは新しい全項目横持ちテーブルは採用しない。

## 良い点

- 年度内複数受診を `person_event` 1件へ誤って統合しない。
- 予約、受領、case、出力、ダッシュボード、納品の正本を維持できる。
- 一覧性能をstatus itemで確保し、詳細では正本まで追跡できる。
- 未突合データを母集団の未実施者へ混ぜない。
- 新しい工程が増えても `person_event` の固定列を増やさずに済む。

## 実装前に守る条件

1. HIA加入者ID単独で予約を自動確定しない。重複時は `MULTIPLE` とする。
2. 予約とcaseの受診日が一致しても、subscriberが未確定なら同一受診として確定しない。
3. ダッシュボードの最新行を過年度eventへ無条件に結び付けない。
4. 健保納品はcaseのXML出力と同じものではない。HIAから取得したXMLと `person_year_id` を経由して表示する。
5. status item同期は自分が所有するitem codeだけを入れ替え、他処理のitemを削除しない。
6. 一覧の総数・工程件数はページ内データから算出しない。
7. PII権限は加入者情報だけでなく予約サイト由来の氏名、電話、住所にも適用する。

## リスクと対策

| リスク | 対策 |
| --- | --- |
| 予約の誤突合 | 明示的linkテーブル、一意性確認、手動確定監査 |
| status itemの陳腐化 | 最終同期日時とsource run IDを表示し、詳細は正本を優先 |
| 複数受診の見落とし | 詳細で予約・ledger・caseを複数行表示 |
| 横断JOINによる画面遅延 | 一覧と詳細の読み取り方式を分離、サーバ側ページング |
| 状態名の意味が領域ごとに違う | 工程別状態を保持し、単一の総合statusへ潰さない |
| スキーマ肥大化 | 新規は予約linkテーブルに限定し、可変状態は縦持ち |

## 段階導入の判定

第一段階は予約突合と一覧の参照表示までとし、自動修正・再実行ボタンは置かない。実行環境で予約の一意突合率、複数候補率、未突合率を確認してから、手動突合画面とattention判定を調整する。

この順序なら、予約CSVを取り込んだ直後から既存データとの接続率を測定でき、誤った自動紐付けを業務状態として固定する危険を抑えられる。
