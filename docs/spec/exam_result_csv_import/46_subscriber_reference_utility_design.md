# 加入者情報確認ユーティリティ 設計

## 1. 目的

2026-08-31初期版実装済み。検索、通常詳細、完全表示詳細、event別状態、ダッシュボード、値を表示しない変更・参照履歴までを参照専用で実装した。

加入者を起点に、現在の登録状態、イベントごとの健診処理状況、ダッシュボード状態、変更履歴を横断確認する参照専用ユーティリティを作る。

健診結果処理そのものではなく「人の確認」が目的であるため、HOMEの健診結果処理グループではなくユーティリティへ配置する。将来、人物に関する参照・調査機能が増えた場合は、人物管理または人物確認のグループへ移す。

初期版は更新、補正、再実行を行わない。必要な操作は既存のledger、case、出力リスト等の画面へ遷移して行う。

## 2. 画面構成

### 2.1 加入者検索

URL案: `/utilities/subscribers`

検索条件:

- HIA加入者ID
- 保険証記号
- 保険証番号
- 氏名カナ
- 生年月日
- 保険者番号
- 社員番号
- subscriber ID

文字列条件は部分一致を基本とする。subscriber IDは数値として解釈できる場合に完全一致を優先する。条件未入力では全件を表示せず、検索条件の入力を求める。

検索結果には、対象者を識別するために必要な最小限の情報だけを表示する。

- subscriber ID
- HIA加入者ID
- 氏名カナのマスク表示
- 生年月日のマスク表示
- 保険者番号
- 記号・番号の末尾等を使ったマスク表示
- 資格状態
- 最新イベント、最新健診日、最新健診処理状態

検索結果の完全な氏名、住所、記号、番号は表示しない。候補の操作には、権限に応じて次の2種類を用意する。

| 操作 | 表示モード |
| --- | --- |
| 詳細（通常） | ユーザーの表示レベルに従い、マスク表示または非表示で開く |
| 個人情報を含む詳細 | `FULL` 権限がある場合だけ表示し、完全表示モードで開く |

詳細を開いた後に完全表示へ切り替える導線は初期版では置かない。完全表示が必要な場合は、検索結果または通常詳細から一覧へ戻り、明示的に `個人情報を含む詳細` を選択する。

### 2.2 加入者詳細

URL案: `/utilities/subscribers/{subscriber_id}`

1ページ内を次のタブで構成する。

1. 概要
2. イベント・健診状況
3. 変更・参照履歴

詳細画面は通常表示と完全表示でサーバ側の表示modeを明確に分ける。通常詳細はGETで開き、完全表示は検索結果の専用フォームをPOSTして開く。完全表示modeをquery parameterだけで許可せず、サーバ側で権限確認と閲覧監査を完了した場合だけ表示する。これによりリンクの先読みやURL共有だけで完全情報が表示されることを避ける。

#### 概要

完全な機微情報を表示せず、登録状態と追跡用IDを中心に表示する。

- subscriber ID
- HIA加入者ID
- identity hashの有無または短縮表示
- 保険者番号
- 記号・番号のマスク表示
- 資格状態、資格喪失日
- 所属事業所ID等の参照ID
- 加入者情報の登録元
- 作成日時、最終更新日時
- 関連event数、ledger数、case数
- 最新のダッシュボード状態

住所、氏名、生年月日等は表示modeに従って、完全表示、マスク表示、または非表示にする。完全表示mode以外では完全な値をDBから画面用modelへ載せない。

### 2.3 個人情報表示レベル

ユーザーごとに次の排他的な表示レベルを持つ。

| レベル | 通常詳細 | 完全表示の導線 |
| --- | --- | --- |
| `FULL` | マスク表示 | 表示する |
| `MASKED` | マスク表示 | 表示しない |
| `HIDDEN` | 個人情報欄を非表示 | 表示しない |

`FULL` のユーザーでも通常詳細はマスク表示を既定とする。完全表示は別のボタンから明示的に開く。複数レベルが同時に設定された不正状態では、より制限の強い `HIDDEN`、`MASKED`、`FULL` の順で適用する。

加入者、event、ledger、case、run等の内部IDと処理状態は、この個人情報表示レベルではなく加入者参照権限で制御する。

#### イベント・健診状況

加入者に関連するeventを新しい順に表示する。

- event ID、イベント名、年度
- `person_event` の有無と状態
- `person_event_status_items` の項目別状態
- HIAダッシュボード状態
- 予約日、受診日、健診機関
- ledger件数とsource形式
- case件数
- case作成、採用値作成、法定チェックの状態
- 理由ありOK、BLOCKED、出力可否
- 出力リスト登録、XML出力、HIA連携の状態
- 最新エラーのログID

イベント行を展開すると、処理フローを次の順で表示する。

```text
加入者・event
  -> 受領ファイル
  -> exam ledger
  -> 加入者突合
  -> case作成・source結合
  -> 採用値作成
  -> 法定チェック・人手判断
  -> 出力リスト
  -> XML出力
  -> HIA連携
```

各工程には状態、件数、最終更新日時、参照IDを表示する。更新操作は置かず、既存の受領ファイル、ledger詳細、case詳細、出力リスト、実行ログへリンクする。

#### 変更・参照履歴

変更履歴と閲覧履歴を同じタブ内の別セクションとして表示する。

変更履歴は `dev_phr.subscriber_audit` を参照し、次だけを表示する。

- audit ID
- 変更日時
- 変更されたfield名
- source
- noteの有無または機微を除いた要約
- change run ID

`old_value` と `new_value` は取得結果に含めず、画面にも出さない。変更者を直接持たない既存行は、change run IDやsourceから追える範囲だけ表示し、推測で操作者を補完しない。

閲覧履歴は `phr_app.app_audit_logs` を参照し、次を表示する。

- app audit log ID
- 閲覧日時
- action code
- app user IDまたは社員番号
- target table、target ID
- event ID、case ID等の関連ID

IPアドレス、User-Agent、画面で表示した機微情報は通常画面には出さない。管理者向け監査ログ画面では既存権限に従う。

## 3. データ取得方針

加入者を正として、関連情報をIDでたどる。

1. `dev_phr.subscribers.id` から加入者の現在状態を取得する。
2. subscriber ID、HIA加入者ID、identity hashを既存の対応関係に従って関連テーブルへ接続する。
3. `person_event` と `person_event_status_items` からevent単位の業務状態を取得する。
4. `health_exam_result.exam_ledgers` から受領sourceと突合状態を集計する。
5. `exam_export_cases`、case sources、case valuesから結合・採用値・check・出力可否を集計する。
6. 出力リスト、XML ZIP/member、HIA状態をcase IDから取得する。
7. `work_other.hia_dashboard_status` は既存のHIA加入者ID等の接続条件を共通化して参照する。
8. `subscriber_audit` と `app_audit_logs` から値を除いた履歴を取得する。

画面専用の状態判定を新設せず、既存ダッシュボード、ledger、case、readinessの状態値をそのまま表示する。複数テーブルで状態が矛盾する場合は上書き統合せず、工程別に並べて不一致が分かるようにする。

## 4. 閲覧監査

既存の `phr_app.app_audit_logs` と `log_audit()` を使うため、新しい監査テーブルは作らない。

初期action code案:

- `PERSONAL_INFO_SEARCH_SUBSCRIBER_UTILITY`
- `PERSONAL_INFO_VIEW_SUBSCRIBER_UTILITY`
- `PERSONAL_INFO_VIEW_SUBSCRIBER_EVENT_UTILITY`
- `PERSONAL_INFO_VIEW_SUBSCRIBER_HISTORY_UTILITY`
- `PERSONAL_INFO_VIEW_SUBSCRIBER_FULL_UTILITY`

検索監査には検索文字列そのものを保存しない。検索種別、結果件数、対象を選択した場合のsubscriber IDだけを記録する。

加入者詳細を開いた時はsubscriber IDをtarget IDとして記録する。完全表示は通常詳細と異なるaction codeで、完全表示ページを返す前に監査記録を保存する。イベント詳細を展開または表示した時はevent ID、case ID等の参照IDを `after_json` に保存してよいが、氏名、住所、生年月日、記号、番号などの完全な値は保存しない。

## 5. 権限

加入者参照、履歴参照、将来の編集を分離し、個人情報には `FULL` / `MASKED` / `HIDDEN` の排他的な表示レベルを設定する。ユーティリティへのリンク、検索、詳細、履歴APIのすべてでサーバ側の権限を確認する。

画面が参照専用でも個人情報へのアクセスであるため、ログイン済みだけでは許可しない。変更履歴と参照履歴は通常の加入者詳細より強い履歴閲覧権限へ分ける。完全表示のボタンを隠すだけでなく、完全表示のURL・APIでも `FULL` を必須とする。

## 6. エラーと不整合表示

- 接続先に行がない場合はエラーにせず「未登録」と表示する。
- subscriber IDはあるがHIA加入者IDがない等の不一致を警告表示する。
- 同じ加入者に同一eventのcaseが複数ある場合は件数とIDを表示する。
- APIエラーは既存の共通処理でログIDと管理者向け詳細リンクを表示する。
- 一部DBの参照に失敗した場合、全画面を空にせず取得できなかったセクションを明示する設計を後続検討する。

## 7. migration・seed

初期版の参照データと監査保存先に、新しい業務テーブルやカラムのmigrationは不要である。一方、権限コード登録のため `20260831_001_phr_app_add_subscriber_reference_permissions.sql` を適用する。

既存の次のテーブルを参照・利用する。

- `dev_phr.subscribers`
- `dev_phr.subscriber_audit`
- `dev_phr.person_event`
- `dev_phr.person_event_status_items`
- `health_exam_result.exam_ledgers`
- `health_exam_result.exam_export_cases` と関連テーブル
- 既存の出力リスト、XML出力履歴テーブル
- `work_other.hia_dashboard_status`
- `phr_app.app_audit_logs`

ただし、実行環境に既存DDLが未適用でテーブル自体がない場合は、その既存migrationを適用する必要がある。今回専用のスキーマ変更は行わない。

加入者参照、履歴参照、編集、個人情報表示レベルは既存のON/OFF権限行で表現し、ユーザー設定画面では表示・編集スイッチと、排他的な個人情報レベル3択として操作する。

実行環境に `person_event` または `person_event_status_items` が未適用でも画面全体をエラーにせず、該当情報を未登録としてledger・case・ダッシュボードを表示する。加入者の世代差で任意カラムがない場合も同様に扱う。

## 8. 初期実装順

1. ユーティリティに「加入者情報確認」を追加する。
2. 加入者検索とマスク済み検索結果を実装する。
3. 加入者詳細の概要を実装する。
4. event・ledger・case・ダッシュボード状態を横断表示する。
5. 既存画面への参照リンクを追加する。
6. 値を表示しない加入者変更履歴を追加する。
7. 閲覧監査を記録し、参照履歴を表示する。
8. 権限、マスク、監査ログに機微情報が入らないことをテストする。

## 9. 初期版の非対象

- 加入者情報の編集
- caseやledgerの更新
- case再実行
- 複数加入者への一括操作
- old value、new valueの表示
- 検索条件への氏名・住所等の完全値保存
- 新しい人物統合・重複解消処理
