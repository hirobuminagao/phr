# 受領alias単位処理 設計レビュー

## 1. 結論

設計は条件付き承認とする。次の5点を満たすことが実装開始条件であり、設計書へ反映済みである。

1. receiptへ受領aliasの系譜を永続化する。
2. alias ledgerで対象受診を見つけ、case構築時は同一受診の全sourceを読む。
3. `03_01`が新規・既存を含む実対象case IDを後続へ渡す。
4. event全体実行を維持する。
5. Windowsのコマンド長を避け、case IDをファイルで渡す。
6. 今回取込分、既存case分、case未成立ledgerを別集合として抽出し、重複caseだけ一意化する。
7. case未成立ledgerをimport失敗と混同せず、修正後に再判定できる状態で記録する。

## 2. 却下した案

### 健診機関IDだけで絞る

同一施設複数aliasと複数施設ZIPを正しく扱えないため却下。`file_receipts.medical_folder_alias_id`を正とする。

### alias由来ledgerだけでcaseを作る

既存MANUAL/PAPER等の補完値が消えるため却下。aliasは対象受診キーの発見だけに使い、同一受診の全sourceを再結合する。

### 新規caseだけ後続へ渡す

既存caseへのsource追加が採用値へ反映されないため却下。更新・再評価した既存caseも含める。

### `03_01`後にaliasからcaseを再検索する

過去caseまで巻き込み、今回の対象を再現できないため非推奨。`03_01`自身がID集合を確定する。

### case IDをCLIへ大量展開する

Windowsのコマンド長制限に達し得るため却下。JSONファイル入力を使う。

## 3. 整合性レビュー

- scan run IDだけの絞り込みでは、取り込み済み再処理を扱えない。
- importが部分失敗した場合、成功分だけ後続へ進めず一括処理を停止する。
- case自然キーの既存方針を維持し、保険者番号不整合の安全停止を緩和しない。
- 同一受診に複数ACTIVE caseがあれば自動統合せず停止する。
- case限定再実行のレビュー保持と自動解消を使い、理由ありOKを一律初期化しない。
- POSTとCLIの両方でeventとaliasの所属を検証する。
- alias無効化後も過去receiptのalias IDを消さない。
- 同一ファイル再検出時のalias補完はNULLだけを対象とし、既存の別alias IDをscanが上書きしない。

### 今回取込と既存取込の分離

一つのaliasスコープだけでは「今追加されたもの」と「以前からあるもの」の区別ができない。今回取込集合はimport runまたは今回処理したreceipt IDで固定し、既存case集合とcase未成立ledger集合はalias系譜から別に取得する必要がある。case作成後、最後にcase IDで和集合を取る。

### case未成立はcaseではない

加入者未突合などは「どのcaseにも当てはまらないcase」ではなく、case未成立ledgerとして扱う。ここをcase行として仮作成すると、重複case・不正なsubscriber・出力候補混入の原因になるため却下する。

import成功とcase成立は別ステータスであり、case未成立ledgerが含まれても一括処理を失敗にしない。一方、成立済みcaseの保険者番号・source所有権競合はデータ破損防止のため停止を維持する。

## 4. 運用レビュー

- aliasは毎回明示選択とし、自動選択しない。
- 0件正常終了と、スコープ不整合による0件を区別する。
- 初期実装ではevent単位排他を維持する。
- 個別`03_02`・`03_04`をaliasだけで実行させない。
- 結果に新規caseと既存更新caseを分けて表示する。
- case未成立ledgerを理由別に確認でき、加入者突合後に再処理できるようにする。

## 5. DB肥大化レビュー

初期実装では実行スコープ専用テーブルを追加しない。永続追加はreceiptのalias IDだけとし、case集合は一時JSONで渡す。

非同期ジョブ化、alias並列実行、過去実行対象の完全再現、画面からの途中再開が必要になった時点で、実行スコープとメンバーの2テーブルを再検討する。現行同期処理に先回りして追加すると管理対象が肥大化する。

## 6. 実装レビュー順序

1. migration・DDL・backfillのdry-run確認
2. 各CLI単体のalias scope確認
3. `03_01`の全source再結合とcase ID出力を重点レビュー
4. event全体実行の回帰確認
5. 管理画面接続
6. Windowsでcase IDファイル経路を確認
7. Dockerで画面と履歴を確認

最優先のレビュー対象は「既存補完sourceを落とさないこと」と「既存更新caseも後続へ渡すこと」である。どちらも誤ると、画面上は成功しても出力値が欠落する。
