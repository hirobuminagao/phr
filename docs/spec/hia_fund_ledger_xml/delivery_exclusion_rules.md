# HIA_fund_ledger_xml Delivery Exclusion Rules

このドキュメントは `HIA_fund_ledger_xml` における **納品再構成時の除外ルール** を整理するためのメモである。

本タスクでは、ledger への取込と Fund 向け納品再構成を分けて考える。
そのため、除外ルールは **取込時には適用せず、納品再構成時に適用する** ことを基本方針とする。

---

# 目的

- 最新分再構成時に除外したい条件を管理できるようにする
- ledger の履歴を消さずに、納品対象だけを制御できるようにする
- 健保ごとの契約差・運用差を吸収できるようにする
- 今後増える可能性のある除外条件に対応できるようにする

---

# 基本方針

## 1 取込では除外しない

除外条件が存在しても、HIA から取得した XML は ledger には記帳対象とする。

理由:

- 元データ履歴を保持したい
- 後で説明可能にしたい
- 納品除外ルールの変更に追従しやすい

つまり、**取込 = 事実の記帳**、**納品 = 出力制御** と分ける。

---

## 2 除外は納品再構成時に適用する

納品対象抽出の流れは概ね以下。

```text
最新月対象抽出
↓
過去登場済み除外
↓
delivery exclusion rules 適用
↓
残った対象で納品 ZIP 再構成
```

---

# 今回明確に分かっている除外ケース

現時点で明確に把握している除外ケースは以下。

- 契約外医療機関の健診結果

背景:

- HIA 側では健診結果 XML が同じ格納先に混在している
- その中には、当社が健診代行契約をしていない医療機関の結果も含まれる
- 特定保健指導のために健保から最低限の情報だけ登録されているケースがある
- これを当社から健保へ再納品すると、業務上の循環・矛盾が発生する

そのため、少なくとも **契約外医療機関** は納品再構成時に除外対象とする。

---

# ルールテーブルの考え方

現時点では、除外ルールは汎用テーブルとして管理する前提とする。

想定テーブル名:

```text
hia_delivery_exclusion_rules
```

想定する保持項目:

|項目|意味|
|---|---|
|insurer_number|保険者番号|
|target_schema|対象 DB / schema 名|
|target_table|対象テーブル名|
|target_column|対象カラム名|
|match_type|一致条件種別|
|match_value|除外判定に使う値|
|reason|除外理由|
|source_note|除外根拠 / 情報源|
|is_enabled|有効フラグ|
|created_at|登録日時|
|updated_at|更新日時|

---

# match_type

現時点では運用主体が限定されているため、許可する条件種別は **運用で制御**する。

ただし設計上は将来拡張を見込んで `match_type` を持つ前提とする。

候補例:

- `eq`
- `contains`
- `startswith`
- `is_null`

v1 ではまず `eq` 中心での運用を想定する。

---

# 今回の具体例

契約外医療機関を除外したい場合の登録イメージ。

|項目|値の例|
|---|---|
|insurer_number|06139463|
|target_schema|work_other|
|target_table|hia_xml_events|
|target_column|facility_code|
|match_type|eq|
|match_value|12345678|
|reason|契約外医療機関|
|source_note|健保から提供|
|is_enabled|1|

---

# ledger に持つべき施設情報

除外条件を成立させるため、ledger 側には医療機関を特定できる情報を保持する前提とする。

少なくとも以下は保持候補。

- `facility_code`
- `facility_name`
- `facility_number`（XML 上の医療機関番号相当）
- `insurer_number`

原則として、一次情報は **xml ledger 側** に保持する。

必要に応じて、人台帳側には代表値を持たせることを検討するが、施設情報の一次情報は XML 単位で持つ前提とする。

---

# なぜ汎用ルールにするか

今明確なケースは契約外医療機関だが、今後は以下のような除外条件が増える可能性がある。

- 特定の医療機関番号
- 特定の施設コード
- 特定の医療機関名
- 特定の値を持つテストデータ
- 健保個別運用による除外条件

そのため、施設専用テーブルではなく、最初から汎用ルールの形を採る。

---

# 運用前提

現時点では運用主体が限定されているため、以下は **運用で制御**する前提とする。

- `target_table` に何を許可するか
- `target_column` に何を許可するか
- `match_type` に何を許可するか

将来、運用者が広がる場合には、許可対象テーブル・カラム・条件種別を別途固定化することを検討する。

# 想定フロー上の位置

```text
HIA ZIP 取込
↓
ledger 記帳
↓
最新月対象抽出
↓
過去登場済み除外
↓
delivery exclusion rules 適用
↓
納品 ZIP 再構成
```

このように、除外ルールは **delivery layer の制御** として位置づける。
