# ADR-0016: v1.1.0 identity layer commonization and backfill

- Status: Proposed
- Date: 2026-03-27
- Version: v1.1.0


## Goal

v1.1.0 のゴールは以下で固定する。

- 人のイベントを安定して管理できる基盤を作ること
- その前提として、パイプライン横断で同一人物をブレずに識別できる identity 基盤を共通ライブラリとして確立すること

本バージョンではイベント管理そのものの完成は目的とせず、その土台となる以下を固定する。

- `person_id_custom` / `identity_hash` の生成ロジック
- field ごとの canonicalization（raw / base_norm / field_norm / match）
- builder による完成値生成責務の分離
- backfill および再生成可能な検証手段の確立

すなわち、v1.1.0 は「人イベント管理のための identity 基盤の確定版」と位置づける。

## Context

v1.0.3 までで、`medi_xml_ledger` への `person_id_custom` / `identity_hash` 導入、および `custom_id_gen` の実効桁判定ルールの固定は完了した。

一方で、現状の identity 系処理はパイプラインごとに分散しており、以下の課題が残っている。

1. 同じ「人物識別」のための正規化でも、利用箇所ごとに関数・責務・入力前提が分かれている。
2. `raw / match / hash` の三段構え方針は定まったが、各スクリプトでの適用位置が揃っていない。
3. `person_id_custom` 生成に必要な前処理と、照合用 `match` 値の前処理が混在しやすい。
4. 既存データに対しては backfill が必要だが、どの列を、どの順で、どのルールで埋めるかの基準を固定しきれていない。
5. freeze 中に局所修正で前進したため、v1.1.0 では「共通化の単位」を明示してから整理しないと、今後の HIA / medi / subscriber 系で再び同種の揺れが発生する。

また、現在の大前提として、今後の設計・実装ルールは次で固定されている。

- 元の値は省かず `raw` を保持する
- 参照・照合用として必ず `match` を作る
- ハッシュ生成に必要な値が揃うなら `hash` を作る
- 参照用（match系）は英数字は半角、先頭0は削除する
- 値の正規化は「全てが数字なら半角」「一文字でも数字以外が入るなら全部全角（厚生労働省フォーマット）」を採用する

v1.1.0 では、freeze 後の整理として、identity 系ロジックを「共通レイヤー」として切り出す方向を明文化し、backfill 方針も同時に固定する必要がある。

この共通 identity 基盤は、それ自体をゴールとするものではなく、後続の XML / CSV チェック処理・人物単位集約・イベント管理の前提となる基盤である。特に SHG（特定保健指導）結果XMLチェック処理では、`shg_result` と結果XMLを同一人物単位で突合するために `person_id_custom` / `identity_hash` を利用する想定となり、後続の構造判断は ADR-0018 へ派生する。

## Decision

v1.1.0 では、identity 系処理を layer / norm / builder の責務ごとに分けて共通化する。詳細な項目別仕様は子specへ委譲するが、本ADRでは上位方針を固定する。

### 1. identity の責務を `raw / base_norm / field_norm / match / builder` に明確分離する

- `raw`
  - 受領した元値を保持する
  - 入力由来の痕跡として保存する
  - 原則として意味変換しない
- `base_norm`
  - 全項目共通の下ごしらえ正規化とする
  - Unicode正規化、空白整理、制御文字除去、空値判定などの「意味を持たない整形」を担う
  - 項目依存の判断は行わない
- `field_norm`
  - 各項目の意味に応じた基本正規化値とする
  - 項目ごとの差分（記号、番号、生年月日、氏名カナ、性別コードなど）はここで担う
- `match`
  - 照合・比較・検索用の正規化値とする
  - 各項目ごとにルールを固定する
  - 原則として `field_norm` を起点に生成する
- `builder`
  - `person_id_custom` や `identity_hash` などの完成値を組み立てる責務とする
  - 必須材料が不足する場合は無理に生成しない

### 2. 共通化対象を「処理単位」で切り出す

identity 共通レイヤーでは、少なくとも以下の単位で関数またはモジュールを分離する。

1. 文字種・空白・記号の基礎正規化（primitive / base_norm）
2. 記号（symbol）用 `field_norm / match`
3. 番号（number）用 `field_norm / match`
4. 保険者番号用 `field_norm / match`
5. 生年月日用 `field_norm / match`
6. 氏名カナ用 `field_norm / match`
7. 性別コード用 `field_norm / match`
8. `person_id_custom` builder
9. `identity_hash` builder
10. DB更新用 backfill ロジック

### 3. `match` 用正規化と `hash` / `person_id_custom` 用正規化を分離する

以下は似ていても責務が異なるため、layer と builder の境界を明示して管理する。

- 画面/DB検索・JOIN 用の `match`
- `person_id_custom` builder に渡す canonical input
- `identity_hash` builder に渡す canonical input

ただし、v1.1.0 の詳細specでは、少なくとも以下については各項目の `match` 値を canonical input として採用する。

- `birthdate_match`
- `insurance_number_match`
- `insurer_number_match`
- `insurance_symbol_match`
- `name_kana_full_match`
- `gender_code_match`

すなわち、責務は分離するが、v1.1.0 時点では canonical input の多くを `match` から流用する。ここで分離するのは「値の意味」ではなく「責務境界」である。

### 4. backfill は「列を埋める順序」を固定する

既存データに対する backfill は、原則として次の順で行う。

1. `raw` 系列の存在確認
2. `base_norm / field_norm / match` 系列の生成
3. `person_id_custom` の生成
4. `identity_hash` の生成
5. 監査・件数確認・差分確認

特に v1.1.0 では、`name_kana_full_match` の正規定義に長音符除去を含めたため、既存 `identity_hash` は再生成 backfill 対象となる。

### 5. v1.1.0 では freeze の破壊を避ける

v1.1.0 は全面的な仕様変更ではなく、v1.0.3 で確定したルールを前提に、以下を目的とした整理版とする。

- 既存ルールの共通レイヤー化
- 重複実装の削減
- backfill 手順の固定
- 今後の subscriber / medi / HIA 系パイプラインへの横展開準備

## Consequences

### Positive

- identity 系処理の責務境界が明確になる
- `match` と `hash` の混同が減る
- backfill 実行時の説明可能性が上がる
- 既存スクリプトを段階的に共通関数へ寄せやすくなる
- 今後の refactor で「何をライブラリ化するか」の単位が明確になる
- `base_norm / field_norm / match / builder` の責務差が明文化され、今後の実装差し替えがしやすくなる
- `person_id_custom` と `identity_hash` の再生成条件を説明しやすくなる
- SHG XMLチェックや今後のCSVチェック処理において、人物突合キーを安定的に供給できる

### Negative / Trade-offs

- 既存コードの呼び出し差し替えに一定の手間がかかる
- 一時的に旧関数と新関数が並存する可能性がある
- `match` と hash canonical の責務分離により、関数数・ファイル数は増える
- backfill 対象テーブルが増えると、テスト観点も増える

## Scope

本ADRの対象は、少なくとも以下に関わる identity 系処理とする。

- `medi_xml_ledger`
- `subscribers`
- `staging_subscribers_hub`
- HIA import / dashboard import 系の人物識別処理
- `custom_id_gen` とその前段の canonicalization

## Out of Scope

本ADRでは、以下は扱わない。

- 付属2や CDA section の業務仕様整理
- XML出力仕様そのものの変更
- freeze 中の挙動を変える大幅な業務ロジック変更
- DBスキーマの全面再設計

## Implementation Notes

- 先に ADR を固定する
- 次に spec へ identity 共通レイヤーの責務・入出力を記述する
- その後、既存スクリプトから共通関数へ段階的に寄せる
- backfill スクリプトはテーブル単位で分け、件数確認と差分確認を伴う
- 既存の freeze ロジックは壊さず、差し替えは小さく進める
- 親specは `docs/spec/identity_canonicalization/v1.1.0_identity_layer_commonization.md` とし、詳細な項目別仕様は `docs/spec/identity_canonicalization/identity_layers_norm_and_purpose.md` を参照する
- 実装上の旧名（例: `gender_code`）が残っていても、仕様上の canonical input 名（例: `gender_code_match`）へ読み替えて整合を取る

## Validation

v1.1.0 の builder 実装について、以下を確認済み。

- `person_id_custom` builder は `resources/identity/custom_id/` 配下の設定・置換表を参照して生成する
- debug 用スクリプト（`scripts/debug_identity/verify_person_id_custom.py`, `scripts/debug_identity/verify_identity_hash.py`）を用いて、raw 値 → field → builder の再生成経路を検証可能とした
- 上記スクリプトにより、`person_id_custom` は既存 DB 格納値およびローカル Excel の初期ロジック結果と一致することを確認した
- `identity_hash` も既存 DB 格納値と一致することを確認した

これにより、v1.1.0 で導入した identity builder 層は、既存実績値と整合することを確認した。
