## DH-20260625-01 / 2026-06-25 13:30 JST

### テーマ
健診結果システムの責務とチェック方針の整理

### 背景
HIA subscriber sync が一旦完了したため、次の対象として健診結果処理リファクタリングの設計を開始。
現行実装調査（Codex・Claude）を参考に、新システムの責務整理を進める。

### 当初の考え
- 健診結果処理は「作成」と「管理」の2責務で考えていた。
- チェックはXMLや健診項目を中心に考えていた。

### 議論
- 保険者変換は共通処理と保険者固有処理を分離する方向とした。
- 性別・生年月日などのチェックは加入者突合へ統合する方向とした。
- 特定健診・法定健診の必須項目チェックは今後ルール化を検討する。
- 健診結果は受診者単位で状態管理し、1名の不足で全体を止めない運用を目指す。
- 医療機関回答待ち、再提出、再提出後比較（値消失を含む）を管理対象とする方向で整理した。
- 予約・受診予定情報と健診結果を突合し、結果未着一覧を管理できるようにする案を整理した。
- 請求（金額）処理は今回のリファクタリング対象外とし、健診結果管理へ責務を限定する。
- 当初は「作成」「管理」の2責務で考えていたが、業務フローを見直した結果、以下を新システムの基本フローとする方向で整理した。
  - 医療機関
  - 受領
  - 必要に応じた健診結果作成
  - 結果管理
  - 保険者変換
  - 納品
- 「受領」と「健診結果作成」は別責務とし、受領したデータを管理する処理と、CSV・XML等から健診結果を生成・補正する処理を分離する方向とした。
- 「結果管理」は健診結果を保管するだけでなく、不足管理・再提出管理・HIA投入可否管理・結果未着管理を含む業務管理の中心とする方向で整理した。
- XMLや健診結果のチェックだけでなく、「届くべき健診結果が届いているか」を確認する未着管理もシステム責務として追加する方向とした。
- 健診結果の受領フォルダ構成について整理した。
  - `01_健診結果（元データ）` は医療機関から受領した原本とし、編集しない。
  - `02_健診結果（編集）` はシステム投入前の最小限の成型（フォルダ構成、ZIP化等）を行う場所として利用する方向で検討する。
  - システム処理はネットワークフォルダを直接利用せず、`data/medical/work` へコピーして実施する。
  - `03_健診結果（アップロードデータ）` は HIA アップロード用成果物の出力先とする。
- ネットワーク共有フォルダは業務運用領域、`data/medical/work` はローカルシステムの作業領域として責務を分離する方向で整理した。
- `data/medical/work` へコピーした処理後データの扱い（削除・保持・アーカイブ等）は別途運用設計する。

### 現時点の考え
健診結果システムは「健診結果を保管するシステム」ではなく、「健診結果の品質・進捗・状態を管理するシステム」として設計を進める。

### 決定事項
- 請求・金額処理は今回対象外。
- 健診結果処理に責務を限定する。
- 受診者単位の状態管理を中心に設計する。

### 保留事項
- 特定健診・法定健診の対象判定条件。
- 必須項目判定ロジック。
- 予約データの正とするデータソース（HIAダッシュボード等）の最終決定。
- 結果未着管理の設計。
- 再提出時の差分判定仕様。
- `data/medical/work` の処理後データ運用（削除・保持・アーカイブ）の決定。

### 根拠
- 現場運用の壁打ち
- Codex調査結果
- Claude調査（実行中、結果未反映）

### 次回検討
- フロー図を業務フローからシステムフローへ詳細化する。
- 各フローに対応するスクリプト・テーブル・状態遷移をマッピングする。
- 結果未着管理フローを整理する。
- 再提出フローを整理する。
- DDLへの反映。
- 状態管理テーブル設計。

## DH-20260625-02 / 2026-06-25 14:30 JST

### テーマ
健診結果データ管理と制度チェック設計

### 背景
健診結果管理システムのフロー整理を進める中で、健診値そのものと制度チェック結果をどのように保持するかを整理した。

### 当初の考え
- 特定健診・法定健診のチェック結果を item_values へ保持する案を検討していた。

### 議論
- item_values は「実際に存在した健診値」を保持するテーブルであり、実施されていない項目や値が存在しない項目は保持しない設計であることを再確認した。
- そのため、不足項目や制度判定結果を item_values に保持する設計は採用しない方向とした。
- 特定健診・法定健診の判定結果は専用のチェック台帳として保持する方向で整理した。
- チェック台帳は「加入者 × 年度」を1レコードとし、人が一覧で確認しやすい横持ちレイアウトとする方向とした。
- 項目追加や制度変更は年度単位で列追加する運用を前提とし、判定ルール自体は別管理とする。
- 特定健診・法定健診の全体判定（OK/NG）と、各項目ごとのOK/NG・理由(reason)を保持する構成を検討する。
- チェック処理は受診者単位で完結させる。
- 処理順序は以下とする方向で整理した。
  - 健診結果読込
  - item_values 登録
  - 特定健診チェック
  - 法定健診チェック
  - チェック台帳更新
  - 状態更新
  - 次の受診者

### 現時点の考え
健診値（事実）と制度チェック結果（判定）は責務を分離して保持する。
健診値は現行設計を維持し、制度チェックは年度単位の専用台帳で管理する。

### 決定事項
- item_values の保持方法は現行設計を維持する。
- 制度チェック結果は専用テーブルで管理する。
- チェック処理は受診者単位で完結させる。

### 保留事項
- チェック台帳の正式テーブル名。
- 各チェック項目の列構成。
- 特定健診・法定健診ルールテーブル設計。

### 根拠
- 現場運用
- 設計レビュー
- 健診結果管理フロー整理

### 次回検討
- チェック台帳DDL設計
- 制度判定ルール設計
- subject_status との関連設計

## DH-20260625-03 / 2026-06-25 18:30 JST

### テーマ
イベントモデル導入とリファクタリングの段階的実装方針

### 背景
対象者管理の設計を進める中で、「年度」を中心とした管理よりも、「健診イベント」を中心とした業務モデルの方が実運用に適していることを再整理した。また、初期実装範囲についても見直しを行った。

### 当初の考え
- 対象者台帳は「加入者 × 年度」を基本単位として管理することを考えていた。
- 初期実装から対象者台帳や集計機能まで実装することを想定していた。

### 議論
- 対象者管理は年度ではなく「健診イベント」を中心とした設計とする方向で整理した。
- 年度はイベントの属性とし、対象者はイベントへ所属するモデルを採用する方向とした。
- 将来的な対象者台帳は `event_id`・`subscriber_id`・`attempt_no` を基本とする構成を想定する。
- 初期実装では対象者台帳は実装対象とせず、XML Ledger をデータ管理の終点とする。
- XML Ledger には `subscriber_id` が設定され、XML単位で品質管理・健診値管理・チェック結果管理まで行うことを初期ゴールとする。
- XML Ledger を基盤とすることで、対象者一覧や集計は Power Query や Excel 等でも作成可能と判断した。
- 初期実装で重要視するのは以下とした。
  - XMLが正しく取り込まれること
  - 加入者へ正しく紐付くこと
  - 健診値が正しく登録されること
  - XML単位で健診項目不足・XMLエラー等を判定できること
- event テーブルは初期段階から用意する方向とした。
- 初期実装では event は運用で固定値を利用し、取り込み設定（YAML）から `event_id` を指定して XML Ledger へ登録する方式とする。
- 年度変更やイベント追加時は設定ファイルを変更することで対応し、本格的なイベント管理は次期バージョンで整備する方向とした。

### 現時点の考え
初期実装では XML品質保証基盤の完成を最優先とする。
対象者管理・イベント管理・集計機能は、その基盤の上へ段階的に追加する。

### 決定事項
- 初期実装は XML Ledger を中心としたデータ基盤までとする。
- XML Ledger には subscribers.id を保持する。
- event の概念は先行導入するが、初期実装では設定ファイルから固定 `event_id` を設定する。

### 保留事項
- event テーブルの正式DDL。
- event_subject（対象者台帳）のDDL設計。
- event と健診コース・対象条件との関連設計。
- 対象者台帳を追加するバージョンのスコープ整理。

### 根拠
- 現場運用
- リファクタリング方針整理
- 将来のイベント管理を見据えた設計検討

### 次回検討
- event テーブルDDL設計
- XML Ledger への event_id 追加
- XML Ledger の責務整理
- 初期実装（v2）スコープ確定
- 次期実装（v3）対象者台帳設計

## DH-20260626-01 / 2026-06-26 09:38 JST

### テーマ
ファイル台帳の責務整理とファイル管理方針の見直し

### 背景
v2 のテーブル設計を進める中で、ファイル管理の責務を再整理した。当初は `file_receipts` と `zip_receipts` を分離する案で検討していたが、「システムが本当に管理したい対象は何か」という観点から再検討を行った。

### 当初の考え
- `file_receipts` と `zip_receipts` を独立したテーブルとして設計することを考えていた。
- ZIP展開結果は専用台帳で管理する想定だった。

### 議論
- システムが管理したい対象は ZIP ではなく「受領したファイル」であることを再確認した。
- 将来的には ZIP・XML・CSV など複数形式を扱うため、ZIP専用テーブルを設けるより、ファイル共通台帳として管理する方が自然であると判断した。
- `file_receipts` はファイル単位で管理し、少なくとも以下の情報を保持する方向で整理した。
  - ファイル種別
  - 保険者番号（ファイルから取得）
  - 提出元健診機関番号
  - 健診医療機関番号
  - 健診医療機関名
- 健診医療機関番号・健診医療機関名は、格納フォルダから取得できる情報も管理対象とする。
- 現時点では `02_健診結果（編集）` と `03_健診結果（アップロードデータ）` はほぼ同一内容となる想定だが、エラー修正や不足項目対応により将来的に差分が発生する可能性がある。
- そのため、将来的にシステムが出力するファイルについても `file_receipts` の管理対象へ含められる設計とする方向で整理した。
- `zip_receipts` は独立テーブル前提とせず、必要になった場合のみ追加する方針とした。

### 初期実装フロー

- `file_receipts` を中心とした初期実装フローを整理した。
- `zip_receipts` は独立した管理テーブルとせず、`file_receipts` の `file_type` による処理分岐として扱う方向とした。
- 初期実装の処理フローは以下を基本とする。

```text
02_健診結果（編集）
  ↓
data/medical/work へコピー
  ↓
file_receipts 登録
  ・ファイル種別
  ・保険者番号
  ・提出元健診機関番号
  ・健診医療機関番号
  ・健診医療機関名
  ・source_path
  ・work_path
  ・SHA256
  ・status
  ↓
ファイル種別で処理分岐
  ├─ ZIP → 展開 → XML検出
  ├─ XML → XML検出
  └─ CSV → （将来対応）
  ↓
xml_ledger 登録
  ・event_id
  ・file_receipt_id
  ・subscriber_id
  ・XML基本情報
  ・XMLチェック結果
  ↓
item_values 登録
  ・実際に存在した健診値のみ登録
  ↓
XML単位チェック
  ・加入者突合
  ・健診項目不足
  ・異常値チェック
  ↓
xml_ledger へチェック結果集約
  ↓
file_receipts へ処理結果サマリー集約
  ↓
HIAアップロード待ち / エラー
```

### 3層構成の考え

- 初期実装では `file_receipts`・`xml_ledger`・`item_values` の3層構成を基本とする。
- `file_receipts` はファイル資産台帳として、入力・出力を含めたファイル単位の管理を担当する。
- `xml_ledger` はXML単位の品質・進捗・業務状態を管理する中心テーブルとする。
- `item_values` は健診値（事実データ）のみを保持し、不足項目や制度判定結果は保持しない。

### 現時点の考え
`file_receipts` は「入力ファイル台帳」ではなく、「システムで扱うファイル資産台帳」として位置付ける。

### 決定事項
- `file_receipts` をファイル管理の中心テーブルとして設計する。
- ZIP専用テーブルは初期実装では作成しない方向とする。
- 将来の出力ファイル管理も考慮した責務とする。

### 保留事項
- 出力ファイル同士の親子関係・世代管理方法。
- ファイルステータス管理の詳細設計。
- 将来的に ZIP 専用管理が必要になった場合のテーブル分離方針。

### 根拠
- v2 テーブル設計レビュー
- 現場運用を踏まえた責務整理

### 次回検討
- `file_receipts` DDL設計
- `xml_ledger` とのリレーション整理
- ファイル管理フローの詳細設計

## DH-20260626-02 / 2026-06-26 11:40 JST

### テーマ
法定健診・特定健診チェック結果台帳の保持方針

### 議論

- 法定健診項目チェックの現行処理を追加調査した。
- `dev_phr.exam_item_master`、`exam_item_groups`、`exam_item_group_members`、`exam_item_group_method_members`、`exam_item_group_identity_members` が法定健診判定ルールの材料として使えることを確認した。
- 現行では `medi_lsio_identity_presence` に `xml_sha256 × group_code × identity_item_code` 単位の存在判定を保持していた。
- `medi_lsio_missing_items` には、代表項目ごとの必須判定・不足判定を縦持ちで保持していた。
- ただし、この方式は1人あたり法定健診項目分の行が発生するため、データ量が大きくなる。
- v2では中間の存在判定テーブルを必須とはせず、`item_values` とルールマスタから判定し、結果を `xml_ledger` とチェック結果台帳へ集約する方向で整理した。
- チェック結果台帳は横持ちを基本とし、法定健診項目・特定健診項目ごとに OK/NG ステータスを保持する方向とした。
- reason は項目ごとに個別カラムを持たず、法定健診用 reason、特定健診用 reason の2カラムに集約する方向とした。
- reason は `胸部X線：項目なし｜聴力：値なし` のように、日本語で人が読める形式とし、`xml_ledger` と JOIN してエクスポート・集計で利用できるようにする。

### 現時点の考え

- `item_values` は実際に存在した健診値のみ保持する。
- 法定健診・特定健診の不足判定結果は、健診値ではなくチェック結果として別管理する。
- v2では、現行の縦持ち中間テーブルをそのまま移設するのではなく、人が確認しやすく集計しやすい横持ちチェック台帳へ整理する。

v2のDB境界・処理単位・ステータス設計方針

`11_v2_script_design_notes.md` と `12_v2_ddl_design_notes.md` の骨子を作成したため、実装前にブレやすい設計判断を整理した。

- 処理系・台帳系は `health_exam_result` に置く。
- v2初期処理は XML/受診者単位で一気通貫に実行する。
- status はシステム処理ステータスと業務フローステータスを分けて設計する。

- `file_receipts` と `xml_ledger` の具体的な status 値。
- HIAアップロード待ちをどのテーブルのどのstatusで最終表現するか。
- `person_event` への書き込みをv2初期に含めるか、後続フェーズにするか。

### 根拠
- v2スクリプト設計メモ
- v2 DDL設計メモ
- 現行実装調査

### テーマ

## DH-20260629-04 / 2026-06-29 14:35 JST

### テーマ
file_receipts のファイル種別共通化と処理対象件数の保持方針

### 背景
`file_receipts` のカラム棚卸しを進める中で、旧 `medi_shared_files` / `medi_zip_receipts` に存在する ZIP専用の判定項目を v2 でどう扱うかを整理した。

旧設計では ZIP を中心に、`is_zip`、`zip_has_xml`、`zip_xml_count`、`zip_xml_checked_at` のような項目を持つ方向が考えられていた。しかし v2 では、ZIP・XML・将来のCSVなど複数のファイル種別を同じ `file_receipts` で扱うため、ZIP専用の項目名をそのまま採用するとCSV対応時に責務が歪む可能性がある。

### 議論
- `file_receipts` は物理ファイルの正台帳であり、`work` 側コピーは一時処理領域であって正台帳ではない。
- `file_receipts` には、`02_健診結果（編集）` 配下でシステム投入対象となったファイル情報、処理時の作業パス、現在の処理状態を保持する必要がある。
- 医療機関からの受領時点では、拡張子・ファイル名・中身の形式に揺れがあり得る。
- ただし、人が `01_健診結果（元データ）` から `02_健診結果（編集）` へコピー・編集する過程で、システム投入可能な形へ整える運用とする。
- そのため、v2のシステムは `02_健診結果（編集）` を入力境界とし、受領時点の不揃いは運用側の前処理で吸収する。
- `file_type` は `02_健診結果（編集）` に配置された時点のファイル種別として判定する。
- `file_type` と実際の中身が一致しない場合や、`processable_count = 0` となる場合は、システム側のエラーチェック対象とする。
- `is_zip` は `file_type` で判定できるため、独立カラムとしては不要と整理した。
- `zip_has_xml` は ZIP 専用の表現だが、本質的には「処理対象データを持つか」という意味である。
- CSVの場合は、データ行が0件、またはヘッダーしかない場合は処理対象なしとしてエラー扱いにする。
- CSVにはヘッダーあり・ヘッダーなしが健診機関ごとに存在し得るため、CSV件数の算出方法はテーブル側ではなく、設定またはスクリプト側の責務とする。
- ZIPの場合はXML件数、XML単体の場合は1件、CSVの場合は設定に従って算出したデータ行数を、共通して `processable_count` に記録する方向とした。
- `processable_count = 0` は処理対象なしとしてエラー扱いにする。
- ファイルの中身を確認した日時は、ZIP専用の `zip_xml_checked_at` ではなく、汎用的な `content_checked_at` として保持する方向とした。
- `stage_status` は廃止ではなく、v2では `file_receipts.status` として再設計し、ファイル単位の総合ステータスを持たせる方向とした。
- `run_id` は共通ETL仕様に従い、`etl_run_id` や `first_seen_run_id` / `last_seen_run_id` など、`etl_runs` への参照として整理する方向とした。

### 現時点の考え
`file_receipts` はZIP専用台帳ではなく、ファイル種別に依存しない物理ファイル台帳とする。

ファイルの中身に処理対象が何件あるかは、ファイル種別ごとの専用カラムではなく、共通概念である `processable_count` として保持する。

受領時点のファイル揺れは `01_健診結果（元データ）` から `02_健診結果（編集）` へ移す人手運用で吸収し、システムは `02_健診結果（編集）` を投入境界として `file_type` と `processable_count` を判定する。

### 決定事項
- `is_zip` は独立カラムとして採用しない。
- `zip_has_xml` は採用せず、処理対象件数は `processable_count` に一般化する。
- `zip_xml_count` は `processable_count` に置き換える。
- `zip_xml_checked_at` は `content_checked_at` に置き換える。
- `file_type` で ZIP / XML / CSV などのファイル種別を表現する。
- `file_type` は `02_健診結果（編集）` に配置された時点の投入ファイル種別とする。
- 受領時点の拡張子・ファイル名・形式の揺れは、`02_健診結果（編集）` へ配置する前の運用で整える。
- `processable_count` は「処理対象として認識したデータ件数」とする。
- `processable_count = 0` はエラー扱いとする。
- `file_type` と中身の不一致、または処理対象件数0件は、システム側のエラーチェック対象とする。
- ZIPの場合、`processable_count` はXML件数とする。
- XML単体の場合、`processable_count` は通常1とする。
- CSVの場合、`processable_count` は設定に従って算出したデータ行数とする。
- CSVのヘッダー有無など、件数算出方法はテーブルではなく設定・スクリプト側の責務とする。
- `stage_status` は `file_receipts.status` として再設計し、ファイル単位の総合ステータスを保持する。
- `run_id` 系は ADR-0023 に従い、`etl_runs` への参照として整理する。

### 保留事項
- `file_receipts.status` の具体的な値。
- `etl_run_id` / `first_seen_run_id` / `last_seen_run_id` の正式な持ち方。
- `content_checked_at` の更新タイミング。
- `processable_count = 0` の場合に設定する `error_code` / `error_message` の設計。
- CSV件数算出設定をどこに持つか。

### 根拠
- ZIP・XML・CSVを同じ `file_receipts` で扱えるようにするため。
- ZIP専用カラムを採用すると、CSV対応時にカラム責務が歪むため。
- 物理ファイル台帳として、人が一覧で処理可否・件数・状態を確認できる必要があるため。
- 受領時点の不揃いをDBで吸収しようとするとテーブル責務が膨らむため、`02_健診結果（編集）` をシステム投入境界として運用とシステムの責務を分けるため。
- CSVのヘッダー有無などは健診機関ごとに異なるため、テーブルではなく設定・スクリプト側で吸収する方が自然であるため。

### 次回検討
- `15_medi_to_v2_column_mapping.md` に `medi_shared_files` / `medi_zip_receipts` から `file_receipts` へのカラム対応を反映する。
- `12_v2_ddl_design_notes.md` の `file_receipts` カラム候補を `file_type` / `processable_count` / `content_checked_at` に寄せる。
- `file_receipts.status` の具体値を整理する。
# New Design History Entry

## DH-20260629-05 / 2026-06-29 14:56 JST

### テーマ
業務台帳に総合判定を保持する方針

### 背景
`xml_ledger` のカラム整理に入る前に、XMLとしてOK/NGか、健診内容チェックとしてOK/NGかをどのテーブルで見えるようにするかを整理した。

正規化だけを考えれば、XMLチェック結果や健診内容チェック結果は `etl_errors` や `exam_check_results` などの詳細テーブルをJOINすれば確認できる。しかし、実運用では人がSQLや一覧画面で状態確認・検索を行うため、詳細根拠を見に行かなくても台帳上で総合判定が確認できる必要がある。

### 議論
- `xml_ledger` はXML単位の基本情報Ledgerであり、XMLそのものの情報、受診者基本情報、加入者照合結果、処理状態を持つ。
- XMLとして読めるか、XML構造としてNGかは `xml_ledger` 上で確認できるようにしたい。
- 健診内容チェックの詳細根拠は `exam_check_results` に保持する。
- ただし、`xml_ledger` だけを見ても、そのXMLが健診内容チェックとしてOKかNGかの結論は分かるようにしたい。
- これは、正規化のためではなく、人が運用調査・障害解析・一覧確認をしやすくするためである。
- `file_receipts.status` と同様に、`xml_ledger` にも総合ステータスやサマリー判定を保持する。
- 詳細根拠は別テーブルに保持し、台帳側には結論のみを冗長保持する。
- これにより、通常確認は台帳単体で行い、詳細調査時のみ `exam_check_results` や `etl_errors` を参照する構造とする。

### 現時点の考え
業務台帳は詳細根拠をすべて保持する場所ではないが、人が最初に確認する入口である。

そのため、`file_receipts` や `xml_ledger` には、詳細根拠ではなく総合判定・現在状態・検索しやすいキーを保持する。

### 決定事項
- `xml_ledger` にはXMLとしての処理可否を示すステータスを保持する。
- `xml_ledger` には健診内容チェックの総合判定を保持する。
- 健診内容チェックの詳細根拠は `exam_check_results` に保持する。
- XML処理エラーや詳細エラーは `etl_errors` などの詳細テーブルに保持する。
- 台帳側には詳細根拠ではなく、人が一覧確認・検索するための結論を冗長保持する。
- 詳細調査時は、`xml_ledger` から `exam_check_results` / `etl_errors` へ辿る。

### 保留事項
- `xml_ledger` に持つXML処理ステータスの正式カラム名。
- `xml_ledger` に持つ健診内容チェック総合判定の正式カラム名。
- `xml_ledger` に保持するエラー件数・警告件数・サマリー文言の有無。
- `file_receipts.status` と `xml_ledger` のステータス値の関係。
- `exam_check_results` の総合判定と `xml_ledger` 側の総合判定をどのタイミングで同期するか。

### 根拠
- 人がSQLや一覧画面で状態確認する際、毎回JOINが必要になると運用負荷が高くなるため。
- 障害解析時に、まず台帳だけでOK/NGの切り分けができる方が調査しやすいため。
- 詳細根拠と一覧用結論を分けることで、正規化と運用性のバランスを取るため。

- `15_medi_to_v2_column_mapping.md` に `medi_xml_ledger` から `xml_ledger` へのカラム対応を記録する。
- `12_v2_ddl_design_notes.md` の `xml_ledger` カラム候補へ反映する。
