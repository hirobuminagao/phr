## 2026-06-25 13:30 JST

### テーマ
健診結果システムの責務とチェック方針の整理

### 背景
HIA subscriber sync が一旦完了したため、次の対象として健診結果処理リファクタリングの設計を開始。
現行実装調査（Codex・Claude）を参考に、新システムの責務整理を進める。

### 当初の考え
- 健診結果処理は「作成」と「管理」の2責務で考えていた。
- チェックはXMLや健診項目を中心に考えていた。

### 議論
- 保険者変換は共通処理と保険者固有処理を分離する方向とした。
- 性別・生年月日などのチェックは加入者突合へ統合する方向とした。
- 特定健診・法定健診の必須項目チェックは今後ルール化を検討する。
- 健診結果は受診者単位で状態管理し、1名の不足で全体を止めない運用を目指す。
- 医療機関回答待ち、再提出、再提出後比較（値消失を含む）を管理対象とする方向で整理した。
- 予約・受診予定情報と健診結果を突合し、結果未着一覧を管理できるようにする案を整理した。
- 請求（金額）処理は今回のリファクタリング対象外とし、健診結果管理へ責務を限定する。
- 当初は「作成」「管理」の2責務で考えていたが、業務フローを見直した結果、以下を新システムの基本フローとする方向で整理した。
  - 医療機関
  - 受領
  - 必要に応じた健診結果作成
  - 結果管理
  - 保険者変換
  - 納品
- 「受領」と「健診結果作成」は別責務とし、受領したデータを管理する処理と、CSV・XML等から健診結果を生成・補正する処理を分離する方向とした。
- 「結果管理」は健診結果を保管するだけでなく、不足管理・再提出管理・HIA投入可否管理・結果未着管理を含む業務管理の中心とする方向で整理した。
- XMLや健診結果のチェックだけでなく、「届くべき健診結果が届いているか」を確認する未着管理もシステム責務として追加する方向とした。
- 健診結果の受領フォルダ構成について整理した。
  - `01_健診結果（元データ）` は医療機関から受領した原本とし、編集しない。
  - `02_健診結果（編集）` はシステム投入前の最小限の成型（フォルダ構成、ZIP化等）を行う場所として利用する方向で検討する。
  - システム処理はネットワークフォルダを直接利用せず、`data/medical/work` へコピーして実施する。
  - `03_健診結果（アップロードデータ）` は HIA アップロード用成果物の出力先とする。
- ネットワーク共有フォルダは業務運用領域、`data/medical/work` はローカルシステムの作業領域として責務を分離する方向で整理した。
- `data/medical/work` へコピーした処理後データの扱い（削除・保持・アーカイブ等）は別途運用設計する。

### 現時点の考え
健診結果システムは「健診結果を保管するシステム」ではなく、「健診結果の品質・進捗・状態を管理するシステム」として設計を進める。

### 決定事項
- 請求・金額処理は今回対象外。
- 健診結果処理に責務を限定する。
- 受診者単位の状態管理を中心に設計する。

### 保留事項
- 特定健診・法定健診の対象判定条件。
- 必須項目判定ロジック。
- 予約データの正とするデータソース（HIAダッシュボード等）の最終決定。
- 結果未着管理の設計。
- 再提出時の差分判定仕様。
- `data/medical/work` の処理後データ運用（削除・保持・アーカイブ）の決定。

### 根拠
- 現場運用の壁打ち
- Codex調査結果
- Claude調査（実行中、結果未反映）

### 次回検討
- フロー図を業務フローからシステムフローへ詳細化する。
- 各フローに対応するスクリプト・テーブル・状態遷移をマッピングする。
- 結果未着管理フローを整理する。
- 再提出フローを整理する。
- DDLへの反映。
- 状態管理テーブル設計。

## 2026-06-25 14:30 JST

### テーマ
健診結果データ管理と制度チェック設計

### 背景
健診結果管理システムのフロー整理を進める中で、健診値そのものと制度チェック結果をどのように保持するかを整理した。

### 当初の考え
- 特定健診・法定健診のチェック結果を item_values へ保持する案を検討していた。

### 議論
- item_values は「実際に存在した健診値」を保持するテーブルであり、実施されていない項目や値が存在しない項目は保持しない設計であることを再確認した。
- そのため、不足項目や制度判定結果を item_values に保持する設計は採用しない方向とした。
- 特定健診・法定健診の判定結果は専用のチェック台帳として保持する方向で整理した。
- チェック台帳は「加入者 × 年度」を1レコードとし、人が一覧で確認しやすい横持ちレイアウトとする方向とした。
- 項目追加や制度変更は年度単位で列追加する運用を前提とし、判定ルール自体は別管理とする。
- 特定健診・法定健診の全体判定（OK/NG）と、各項目ごとのOK/NG・理由(reason)を保持する構成を検討する。
- チェック処理は受診者単位で完結させる。
- 処理順序は以下とする方向で整理した。
  - 健診結果読込
  - item_values 登録
  - 特定健診チェック
  - 法定健診チェック
  - チェック台帳更新
  - 状態更新
  - 次の受診者

### 現時点の考え
健診値（事実）と制度チェック結果（判定）は責務を分離して保持する。
健診値は現行設計を維持し、制度チェックは年度単位の専用台帳で管理する。

### 決定事項
- item_values の保持方法は現行設計を維持する。
- 制度チェック結果は専用テーブルで管理する。
- チェック処理は受診者単位で完結させる。

### 保留事項
- チェック台帳の正式テーブル名。
- 各チェック項目の列構成。
- 特定健診・法定健診ルールテーブル設計。

### 根拠
- 現場運用
- 設計レビュー
- 健診結果管理フロー整理

### 次回検討
- チェック台帳DDL設計
- 制度判定ルール設計
- subject_status との関連設計

## 2026-06-25 18:30 JST

### テーマ
イベントモデル導入とリファクタリングの段階的実装方針

### 背景
対象者管理の設計を進める中で、「年度」を中心とした管理よりも、「健診イベント」を中心とした業務モデルの方が実運用に適していることを再整理した。また、初期実装範囲についても見直しを行った。

### 当初の考え
- 対象者台帳は「加入者 × 年度」を基本単位として管理することを考えていた。
- 初期実装から対象者台帳や集計機能まで実装することを想定していた。

### 議論
- 対象者管理は年度ではなく「健診イベント」を中心とした設計とする方向で整理した。
- 年度はイベントの属性とし、対象者はイベントへ所属するモデルを採用する方向とした。
- 将来的な対象者台帳は `event_id`・`subscriber_id`・`attempt_no` を基本とする構成を想定する。
- 初期実装では対象者台帳は実装対象とせず、XML Ledger をデータ管理の終点とする。
- XML Ledger には `subscriber_id` が設定され、XML単位で品質管理・健診値管理・チェック結果管理まで行うことを初期ゴールとする。
- XML Ledger を基盤とすることで、対象者一覧や集計は Power Query や Excel 等でも作成可能と判断した。
- 初期実装で重要視するのは以下とした。
  - XMLが正しく取り込まれること
  - 加入者へ正しく紐付くこと
  - 健診値が正しく登録されること
  - XML単位で健診項目不足・XMLエラー等を判定できること
- event テーブルは初期段階から用意する方向とした。
- 初期実装では event は運用で固定値を利用し、取り込み設定（YAML）から `event_id` を指定して XML Ledger へ登録する方式とする。
- 年度変更やイベント追加時は設定ファイルを変更することで対応し、本格的なイベント管理は次期バージョンで整備する方向とした。

### 現時点の考え
初期実装では XML品質保証基盤の完成を最優先とする。
対象者管理・イベント管理・集計機能は、その基盤の上へ段階的に追加する。

### 決定事項
- 初期実装は XML Ledger を中心としたデータ基盤までとする。
- XML Ledger には subscribers.id を保持する。
- event の概念は先行導入するが、初期実装では設定ファイルから固定 `event_id` を設定する。

### 保留事項
- event テーブルの正式DDL。
- event_subject（対象者台帳）のDDL設計。
- event と健診コース・対象条件との関連設計。
- 対象者台帳を追加するバージョンのスコープ整理。

### 根拠
- 現場運用
- リファクタリング方針整理
- 将来のイベント管理を見据えた設計検討

### 次回検討
- event テーブルDDL設計
- XML Ledger への event_id 追加
- XML Ledger の責務整理
- 初期実装（v2）スコープ確定
- 次期実装（v3）対象者台帳設計

## 2026-06-26 09:38 JST

### テーマ
ファイル台帳の責務整理とファイル管理方針の見直し

### 背景
v2 のテーブル設計を進める中で、ファイル管理の責務を再整理した。当初は `file_receipts` と `zip_receipts` を分離する案で検討していたが、「システムが本当に管理したい対象は何か」という観点から再検討を行った。

### 当初の考え
- `file_receipts` と `zip_receipts` を独立したテーブルとして設計することを考えていた。
- ZIP展開結果は専用台帳で管理する想定だった。

### 議論
- システムが管理したい対象は ZIP ではなく「受領したファイル」であることを再確認した。
- 将来的には ZIP・XML・CSV など複数形式を扱うため、ZIP専用テーブルを設けるより、ファイル共通台帳として管理する方が自然であると判断した。
- `file_receipts` はファイル単位で管理し、少なくとも以下の情報を保持する方向で整理した。
  - ファイル種別
  - 保険者番号（ファイルから取得）
  - 提出元健診機関番号
  - 健診医療機関番号
  - 健診医療機関名
- 健診医療機関番号・健診医療機関名は、格納フォルダから取得できる情報も管理対象とする。
- 現時点では `02_健診結果（編集）` と `03_健診結果（アップロードデータ）` はほぼ同一内容となる想定だが、エラー修正や不足項目対応により将来的に差分が発生する可能性がある。
- そのため、将来的にシステムが出力するファイルについても `file_receipts` の管理対象へ含められる設計とする方向で整理した。
- `zip_receipts` は独立テーブル前提とせず、必要になった場合のみ追加する方針とした。

### 議論（追記）

- `file_receipts` を中心とした初期実装フローを整理した。
- `zip_receipts` は独立した管理テーブルとせず、`file_receipts` の `file_type` による処理分岐として扱う方向とした。
- 初期実装の処理フローは以下を基本とする。

```text
02_健診結果（編集）
  ↓
data/medical/work へコピー
  ↓
file_receipts 登録
  ・ファイル種別
  ・保険者番号
  ・提出元健診機関番号
  ・健診医療機関番号
  ・健診医療機関名
  ・source_path
  ・work_path
  ・SHA256
  ・status
  ↓
ファイル種別で処理分岐
  ├─ ZIP → 展開 → XML検出
  ├─ XML → XML検出
  └─ CSV → （将来対応）
  ↓
xml_ledger 登録
  ・event_id
  ・file_receipt_id
  ・subscriber_id
  ・XML基本情報
  ・XMLチェック結果
  ↓
item_values 登録
  ・実際に存在した健診値のみ登録
  ↓
XML単位チェック
  ・加入者突合
  ・健診項目不足
  ・異常値チェック
  ↓
xml_ledger へチェック結果集約
  ↓
file_receipts へ処理結果サマリー集約
  ↓
HIAアップロード待ち / エラー
```

### 現時点の考え（追記）

- 初期実装では `file_receipts`・`xml_ledger`・`item_values` の3層構成を基本とする。
- `file_receipts` はファイル資産台帳として、入力・出力を含めたファイル単位の管理を担当する。
- `xml_ledger` はXML単位の品質・進捗・業務状態を管理する中心テーブルとする。
- `item_values` は健診値（事実データ）のみを保持し、不足項目や制度判定結果は保持しない。

### 現時点の考え
`file_receipts` は「入力ファイル台帳」ではなく、「システムで扱うファイル資産台帳」として位置付ける。

### 決定事項
- `file_receipts` をファイル管理の中心テーブルとして設計する。
- ZIP専用テーブルは初期実装では作成しない方向とする。
- 将来の出力ファイル管理も考慮した責務とする。

### 保留事項
- 出力ファイル同士の親子関係・世代管理方法。
- ファイルステータス管理の詳細設計。
- 将来的に ZIP 専用管理が必要になった場合のテーブル分離方針。

### 根拠
- v2 テーブル設計レビュー
- 現場運用を踏まえた責務整理

### 次回検討
- `file_receipts` DDL設計
- `xml_ledger` とのリレーション整理
- ファイル管理フローの詳細設計
